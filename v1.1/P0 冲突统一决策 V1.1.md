## 逐条落地规则

### A1. 费用尾差分配（已定 → **已实现**）
- 规则：本车费用先全精度计算 → 按人数平摊 → 展示时统一四舍五入到 2 位小数 → **无法整除的尾差（通常 1 分）由本车接人顺序排在第一位的乘客承担**。
- 例：车费 100 元 3 人，平摊 33.3333…，展示 33.33 / 33.33 / 33.34，33.34 由接人顺序第 1 位乘客支付。
- 接人顺序以**最终方案复核后的顺序**为准，不在 ALNS 中间步骤定。
- **技术方案第十一节整段改写**：删掉"分摊金额最高者 / 乘客 ID 最小者"的表述。

> **实现补充（2026-10-14）**：以上规则的「第一位」在集合模式下即上车顺序第一位；
> **散场模式下所有人在活动点同时上车、不存在上车顺序**，本实现统一取
> **沿最终路线的访问顺序第一位（即第一位被送达者）**，保持确定性。
> 详见《A1 费用分摊与个人乘车明细实现说明.md》第 3 节，建议回写进技术方案第十一节。

### A2. 6 人优先（推翻原业务需求）→ **已实现**
- 新规则：
  - 乘客数 5~6 人：只能用 6 人车。
  - 乘客数 ≤4 人：**优先用 6 人车尝试合并**（把邻近的 4 人组塞进 6 人车，减少车辆数 = 减少 16 元起步价）；如果合并后路线超过 5400 秒或绕路导致费用上升，则拆回 4 人车。
  - 车型仍是可行性变量，不是成本变量——但"优先 6 人"是默认分组倾向，不是硬约束。
- 算法详细设计第四节改为："容量拆分时优先按 6 人车型切分（如 14 人 → 6+6+2），4 人组在 ALNS 修复阶段尝试与邻近组合并为 6 人车。"
- 业务需求第 15 行原句"因此不存在 6 人车型优先"删除，改为"默认倾向 6 人车型以减少固定成本，但需通过费用/时间评价函数验证，超时即拆 4 人车"。

> **实现补充（2026-10-14）**：本实现先澄清了一处语义——**4 座与 6 座的起步价、里程单价完全相同**
> （《算法详细设计 V1.1》§2 与《技术方案设计 V1.1》原文均已写明"车型不参与费用"），
> 因此「车型」是**纯可行性变量**，真实成本杠杆只有**车数**。据此落地为：
>
> 1. **「优先 6 人」落在分组粒度上**：搜索一律按 6 座装填（14 人 → 6+6+2），
>    车型**不进搜索状态**（`Vehicle` dataclass 未加字段），故搜索空间与 A2 之前逐位一致；
> 2. **解定稿后按每辆车实际载客数派车**：≤4 人 → 4 座，5~6 人 → 6 座（硬规则）。
>    `auto` 取「最小够用」口径，使 `four_seat_count` / `six_seat_count` 成为**真实可执行的派车清单**
>    （原实现恒为 0 / vehicle_count）。备选口径「一律贴 6 座标签」会使 4 座车永不出现，A2 不可观测，未采用；
> 3. **容量上限做成可选**（`vehicle_pref` = auto / six / four），对应《前端产品设计 V1.1》
>    第 220-224 行「自动选择 / 仅4座 / 仅6座」单选——该选择器此前只存在于设计稿，本次才真正实现；
> 4. **新增 `destroy_over_time` 定向拆车算子**，专治「初始解自带超时车」（散场模式实测出现过 5984s > 5400s）。
>    该算子仅在确有超时车时进入算子轮盘，**可行实例的随机轨迹与 A2 之前逐位一致**（测试用计数器桩断言调用 0 次）；
> 5. **实测代价**：`four`（上限 4）相对 `auto` 平均多派 +2.0 辆车、多花 +15.93%（区间 10.75%~21.04%）——
>    这是「车队只有 4 座车」的硬代价，本次首次量化。
>
> 详细设计、不变性证据、三档对照数据见《A2 车型混用实现说明.md》；
> 原始数据见 `backend/tests/a2_vehicle_compare_result.txt`。

### A3. 开放三种优化模式（V1.0 就上线）
- 前端创建任务页保留三选一：**最省钱 / 平衡 / 少车辆**。
- 数据库 `carpool_task.optimization_mode` 字段枚举值：`cost` / `balanced` / `fewest_vehicles`。
- 三种模式的评价函数定义（默认值，待算法原型调参后固化）：

| 模式 | 排序/权重 | 说明 |
|---|---|---|
| `cost`（最省钱，默认） | 字典序 (total_cost, total_duration, vehicle_count) | 当前已实现逻辑 |
| `fewest_vehicles`（少车辆） | 字典序 (vehicle_count, total_cost, total_duration) | 车辆数绝对优先，费用只在车辆数相同时比较 |
| `balanced`（平衡） | 加权和，先归一化再加权：<br>score = 0.5 × cost_norm + 0.3 × time_norm + 0.2 × vehicle_norm | 见下方归一化口径 |

- **归一化口径**（解决量纲不同问题）：
  - `cost_norm = total_cost / baseline_cost`（baseline_cost = 全部乘客单独叫车的费用总和，用矩阵数据预先算出）
  - `time_norm = total_duration / (n × 5400)`（n=人数，最差情况分母）
  - `vehicle_norm = vehicle_count / n`
  - 三个值都是"约等于 1"的比例数，可直接加权。
- 业务需求第 58 行"V1.0 不开放模式选择"改为"V1.0 开放三种模式，权重为默认值，V2.0 再开放自定义权重"。
- 业务需求第 60 行 weight 字段保留为架构预留，V1.0 不暴露给用户。

### A4. 初始解 60 秒口径
- 阶段切分明确：
  - **阶段 0（前置 IO，不计入算法预算）**：地址解析 <10 秒 + 坐标转换 + 路网矩阵生成 <60 秒。
  - **阶段 1（初始解预算）**：矩阵就绪起算，60 秒内必须出第一个可行方案。
  - **阶段 2（优化预算）**：初始解之后 300 秒。
- 用户实际等待 = 阶段 0 + 阶段 1 + 阶段 2，最长约 370 秒；但"初始解"指的是阶段 1 结束后立刻可以看到的那个方案（不一定最优），用户不需要等 300 秒优化完才能看到结果。
- 前端等待页分两段：
  - "正在获取地图数据…"（阶段 0）
  - "正在优化拼车方案，当前费用 XX 元…"（阶段 1+2，实时刷新）
- 业务需求第 62 行加注释："60 秒初始解预算从矩阵就绪起算，不含地址解析与矩阵生成时间。"

### A5. Top-K 边界与动态扩展
- 边界统一用左闭右开区间：

| 人数 n | 默认 K |
|---|---|
| 1 ≤ n < 10 | 100 |
| 10 ≤ n < 20 | 300 |
| 20 ≤ n < 30 | 500 |
| n ≥ 30 | 1000 |

- 动态扩展：优化过程中连续 60 秒无改善时，K × 2，最大 Kmax = 2000，不再扩大。
- **算法详细设计第十三节补全**：把 Kmax=2000 和动态扩展机制写进去。

### A6. 方案对比页
- 前端设计第十节整节标注："**V1.5 再做**，V1.0 不实现"。
- 方案总览页只展示当前最优方案的总览卡片（费用 / 车辆数 / 人数 / 最长路线 / 求解状态）。
- 数据库 solution 表的 version/is_best 字段保留（为 V1.5 多方案对比预留），但 V1.0 每次任务只保留一个 is_best=1 的方案。

### A7. 改用 SQLite 3（重大架构调整）
- **数据库**：MySQL 8 → SQLite 3（文件型，随项目目录走，不装服务）。
- **缓存**：Redis 去掉，矩阵缓存和优化状态直接放内存（Python dict）+ SQLite 持久化。
- **polyline**：直接存 SQLite 表字段（TEXT 类型），不用 OSS/MinIO。
- **部署**：从"8 核 16G 单服务器"降级为"任意一台能跑 Python 的机器（本机 / 云主机 / 笔记本）"，单机单进程。
- **MVP 团队**：从"3 人团队（后端/算法/前端）"收敛为"1~2 人全栈"，8 周排期可压缩到 4~6 周。
- **表结构基本不变**，字段类型小调整：
  - `bigint` → `INTEGER`
  - `decimal(10,2)` → `REAL`
  - `datetime` → `TEXT`（ISO8601 字符串）
  - `json` → `TEXT`（Python json.dumps）
- **user 表去留**：V1.0 单机工具，**不做登录**，user 表整个删掉；多用户隔离留到 V2.0。
- 数据库设计文档第二章"数据库选型"整节改写。

> **实现补充（2026-10-14）**：矩阵缓存的唯一键从 `(task_id, 点)` 改为
> **`(provider, from_point, to_point)` 点对**，从而**跨任务复用**——同一批地址二次提交零 API 请求。
> 另为「重启后无损恢复」追加两列：`vehicle_route.coordinates` / `leg_durations`
> （只存 polyline 画不出站点与时间线）。单机无迁移框架，老库靠
> `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 就地补列。
> 详见《A7-A8 实现说明.md》§2。

### A8. 求解状态枚举补全
- `optimization_job.status` 字段枚举值（8 种）：

| 状态 | 含义 |
|---|---|
| `INIT` | 刚创建，还在准备矩阵 |
| `FEASIBLE` | 已找到第一个可行方案（优化中） |
| `OPTIMIZING` | 优化进行中 |
| `STOP_GAP` | gap ≤ 5% 提前结束 |
| `STOP_TIMEOUT` | 总预算（300 秒）用尽 |
| `STOP_STABLE` | 连续 60 秒无改善 |
| `OPTIMAL` | gap=0，已证明全局最优 |
| `FAILED` | 未找到可行方案 |

- `FAILED` 再拆 sub_status：
  - `PROVEN_INFEASIBLE`（直达超时等已数学证明不可行）
  - `SEARCH_FAILED`（搜索预算内没找到，不代表数学上不存在）
- WebSocket 推送消息体同步加上 status 字段（见评审意见 B3）。

> **实现补充（2026-10-14）**：三层状态各自归属不混用——任务层 `carpool_task.status`（5 态）、
> 作业层 `optimization_job.status`（8 态）、细分层 `sub_status`；旧客户端的
> `PENDING/RUNNING/DONE/FAILED` 经 `LEGACY_STATUS` 映射兼容，旧前端零改动。
> 需注意：由于费用下界偏松（为了严格成立而放弃 5400s 与车数上限约束），
> **`STOP_GAP` 与 `OPTIMAL` 在正常规模实际不可触发**，真正生效的提前终止是 `STOP_STABLE`。
> 详见《A7-A8 实现说明.md》§3、§4。

### A9. 人均车费上限与「人工确认淘汰」（2026-10-14 新增）→ **已实现**

业务诉求原文：「集合场景下远端乘客会拉高整体费用，实际业务中可以剔除他们；
且需要控制平均到每个人身上的车费，例如人均不能超过 10 元。」

- **口径（业务方确认，实现不得偏离）**：

| # | 口径 |
|---|---|
| B1 | 人均车费 = **拼车总费用 ÷ 参与人数**，**乘客实付**，无平台补贴 |
| B2 | 被剔除者**不再参加活动**——不计入分母、不产生成本、不进方案 |
| B3 | 超限时**算法只给建议**，人工确认后才剔除 |
| B4 | 剔除要**精确到人**——主键是乘客**稳定 id**，不是姓名（同名不可连坐） |

- **新增请求参数**：`per_capita_cap`（人均上限，`null`=不约束）、
  `exclude_ids`（人工确认后的剔除名单，**稳定 id**）、`passengers[].id`（稳定 id，可选）。
- **新增响应字段**：`served_count` / `per_capita_cost` / `per_capita_cap` /
  `excluded_ids`（主键）/ `excluded_names`（展示）/ `exceeded` / `drop_suggestion`。
- **不新增任务状态**：超限时本轮正常完成并附带建议；人工确认后**发起新的求解**，
  避免破坏 A8 已定稿的 8 态枚举。
- 数据库：`carpool_task` 就地补列 `per_capita_cap` / `excluded_ids` / `excluded_names`，
  `passenger.ext_id` / `route_passenger.passenger_ext_id`（老库自动升级）；
  人均**不存列**，由「总费用 ÷ route_passenger 行数」现算。

> **实现补充（2026-10-14 第二版）**：业务反馈两点，均已落地——
> ①**剔除主键改为稳定 id**（原先按姓名剔，两个同名乘客会被一起剔掉，被连坐者凭空失去资格）；
> 前端每行分配 `p1/p2/…`（只增不减、删行不重排），全链路（请求/建议/结果/落库）都以 id 为准，
> 缺 id 的旧客户端按顺序回退 `P001…`，id 重复直接 400。
> ②**人均上限改为下拉选项**（不限 + ¥2 起、步进 ¥2，到 ¥30）——业务反馈「不一定非得是 10」，
> 要的是能快速横向对比不同上限下的方案，下拉比数字框更省事且不会输非法值。

> **实现补充（2026-10-14）**：实现前先做了量化论证，推翻了一处朴素假设——
> **总费用是「车数」的阶梯函数**（1/2/3/4 车 = ¥77.62 / ¥154.90 / ¥212.78 / ¥367.36），
> 因此**剔人并非单调降低人均**：剔除一个人而车数不变时，分子几乎不动、分母 −1，人均必然上涨。
> 实测剔掉**最远**的那位乘客，总费用反而从 ¥212.78 升到 ¥222.66。
> 故候选集必须覆盖「**整车剔除**」一族（只有它才可能真正减一辆车），不能只按距离剔人。
> **重要限制**：实测该 15 人实例人均最低只能做到 **¥12.91**（12 人 2 车），
> **人均 10 元在分散分布下物理不可达**；机制会如实报告不可达并给出根因（车均里程）与整改建议。
> 建议业务先把上限设在 **13~14**，或先确认真实活动的出行集中度。
> 详见《A9 人均车费上限与人工确认淘汰实现说明.md》。

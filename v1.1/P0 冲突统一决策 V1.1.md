## 逐条落地规则

### A1. 费用尾差分配（已定）
- 规则：本车费用先全精度计算 → 按人数平摊 → 展示时统一四舍五入到 2 位小数 → **无法整除的尾差（通常 1 分）由本车接人顺序排在第一位的乘客承担**。
- 例：车费 100 元 3 人，平摊 33.3333…，展示 33.33 / 33.33 / 33.34，33.34 由接人顺序第 1 位乘客支付。
- 接人顺序以**最终方案复核后的顺序**为准，不在 ALNS 中间步骤定。
- **技术方案第十一节整段改写**：删掉"分摊金额最高者 / 乘客 ID 最小者"的表述。

### A2. 6 人优先（推翻原业务需求）
- 新规则：
  - 乘客数 5~6 人：只能用 6 人车。
  - 乘客数 ≤4 人：**优先用 6 人车尝试合并**（把邻近的 4 人组塞进 6 人车，减少车辆数 = 减少 16 元起步价）；如果合并后路线超过 5400 秒或绕路导致费用上升，则拆回 4 人车。
  - 车型仍是可行性变量，不是成本变量——但"优先 6 人"是默认分组倾向，不是硬约束。
- 算法详细设计第四节改为："容量拆分时优先按 6 人车型切分（如 14 人 → 6+6+2），4 人组在 ALNS 修复阶段尝试与邻近组合并为 6 人车。"
- 业务需求第 15 行原句"因此不存在 6 人车型优先"删除，改为"默认倾向 6 人车型以减少固定成本，但需通过费用/时间评价函数验证，超时即拆 4 人车"。

### A3. 开放三种优化模式（V1.0 就上线）
- 前端创建任务页保留三选一：**最省钱 / 平衡 / 少车辆**。
- 数据库 `carpool_task.optimization_mode` 字段枚举值：`cost` / `balanced` / `fewest_vehicles`。
- 三种模式的评价函数定义（默认值，待算法原型调参后固化）：

| 模式 | 排序/权重 | 说明 |
|---|---|---|
| `cost`（最省钱，默认） | 字典序 (total_cost, total_duration, vehicle_count) | 当前已实现逻辑 |
| `fewest_vehicles`（少车辆） | 字典序 (vehicle_count, total_cost, total_duration) | 车辆数绝对优先，费用只在车辆数相同时比较 |
| `balanced`（平衡） | 加权和，先归一化再加权：<br>score = 0.5 × cost_norm + 0.3 × time_norm + 0.2 × vehicle_norm | 见下方归一化口径 |

- **归一化口径**（解决量纲不同问题）：
  - `cost_norm = total_cost / baseline_cost`（baseline_cost = 全部乘客单独叫车的费用总和，用矩阵数据预先算出）
  - `time_norm = total_duration / (n × 5400)`（n=人数，最差情况分母）
  - `vehicle_norm = vehicle_count / n`
  - 三个值都是"约等于 1"的比例数，可直接加权。
- 业务需求第 58 行"V1.0 不开放模式选择"改为"V1.0 开放三种模式，权重为默认值，V2.0 再开放自定义权重"。
- 业务需求第 60 行 weight 字段保留为架构预留，V1.0 不暴露给用户。

### A4. 初始解 60 秒口径
- 阶段切分明确：
  - **阶段 0（前置 IO，不计入算法预算）**：地址解析 <10 秒 + 坐标转换 + 路网矩阵生成 <60 秒。
  - **阶段 1（初始解预算）**：矩阵就绪起算，60 秒内必须出第一个可行方案。
  - **阶段 2（优化预算）**：初始解之后 300 秒。
- 用户实际等待 = 阶段 0 + 阶段 1 + 阶段 2，最长约 370 秒；但"初始解"指的是阶段 1 结束后立刻可以看到的那个方案（不一定最优），用户不需要等 300 秒优化完才能看到结果。
- 前端等待页分两段：
  - "正在获取地图数据…"（阶段 0）
  - "正在优化拼车方案，当前费用 XX 元…"（阶段 1+2，实时刷新）
- 业务需求第 62 行加注释："60 秒初始解预算从矩阵就绪起算，不含地址解析与矩阵生成时间。"

### A5. Top-K 边界与动态扩展
- 边界统一用左闭右开区间：

| 人数 n | 默认 K |
|---|---|
| 1 ≤ n < 10 | 100 |
| 10 ≤ n < 20 | 300 |
| 20 ≤ n < 30 | 500 |
| n ≥ 30 | 1000 |

- 动态扩展：优化过程中连续 60 秒无改善时，K × 2，最大 Kmax = 2000，不再扩大。
- **算法详细设计第十三节补全**：把 Kmax=2000 和动态扩展机制写进去。

### A6. 方案对比页
- 前端设计第十节整节标注："**V1.5 再做**，V1.0 不实现"。
- 方案总览页只展示当前最优方案的总览卡片（费用 / 车辆数 / 人数 / 最长路线 / 求解状态）。
- 数据库 solution 表的 version/is_best 字段保留（为 V1.5 多方案对比预留），但 V1.0 每次任务只保留一个 is_best=1 的方案。

### A7. 改用 SQLite 3（重大架构调整）
- **数据库**：MySQL 8 → SQLite 3（文件型，随项目目录走，不装服务）。
- **缓存**：Redis 去掉，矩阵缓存和优化状态直接放内存（Python dict）+ SQLite 持久化。
- **polyline**：直接存 SQLite 表字段（TEXT 类型），不用 OSS/MinIO。
- **部署**：从"8 核 16G 单服务器"降级为"任意一台能跑 Python 的机器（本机 / 云主机 / 笔记本）"，单机单进程。
- **MVP 团队**：从"3 人团队（后端/算法/前端）"收敛为"1~2 人全栈"，8 周排期可压缩到 4~6 周。
- **表结构基本不变**，字段类型小调整：
  - `bigint` → `INTEGER`
  - `decimal(10,2)` → `REAL`
  - `datetime` → `TEXT`（ISO8601 字符串）
  - `json` → `TEXT`（Python json.dumps）
- **user 表去留**：V1.0 单机工具，**不做登录**，user 表整个删掉；多用户隔离留到 V2.0。
- 数据库设计文档第二章"数据库选型"整节改写。

### A8. 求解状态枚举补全
- `optimization_job.status` 字段枚举值（8 种）：

| 状态 | 含义 |
|---|---|
| `INIT` | 刚创建，还在准备矩阵 |
| `FEASIBLE` | 已找到第一个可行方案（优化中） |
| `OPTIMIZING` | 优化进行中 |
| `STOP_GAP` | gap ≤ 5% 提前结束 |
| `STOP_TIMEOUT` | 总预算（300 秒）用尽 |
| `STOP_STABLE` | 连续 60 秒无改善 |
| `OPTIMAL` | gap=0，已证明全局最优 |
| `FAILED` | 未找到可行方案 |

- `FAILED` 再拆 sub_status：
  - `PROVEN_INFEASIBLE`（直达超时等已数学证明不可行）
  - `SEARCH_FAILED`（搜索预算内没找到，不代表数学上不存在）
- WebSocket 推送消息体同步加上 status 字段（见评审意见 B3）。

> 状态：**已实现并验证**（2026-10-14）

## 1. 为什么做这两项

实现前系统有两处「账面闭环不了」的地方：

**其一，结果只活在进程内存里。** `TASKS = {}` 是个模块级 dict，服务一重启，
所有历史任务、矩阵缓存、优化结果全部蒸发。而 P0/A7 早已把数据库从
MySQL + Redis + OSS 拍板降到**单文件 SQLite 3**，属于「已决策、未落地」。

**其二，求解状态只有 4 种。** 旧枚举 `PENDING / RUNNING / DONE / FAILED`
无法回答用户最关心的两个问题：

- 这个方案是**跑满预算**出来的，还是**提前收敛**、还有提升空间？
- 如果失败，是**数学上根本不可行**，还是**搜索没搜到**（再给点时间也许就行）？

A8 把 `optimization_job.status` 补到 8 种并给 `FAILED` 加 `sub_status` 细分，
正是为了把这两个问题从「算法内部日志」提升到「对外可读的状态」。

两项都零算法风险：A7 是 IO 层包裹，A8 是终止判据 + 状态机，均不触碰
已验证的 ALNS / 2-opt / DBSCAN 寻优链路。

## 2. A7：SQLite 持久化层

### 2.1 选型与落点

| 项 | 决策 | 实现 |
|---|---|---|
| 存储引擎 | SQLite 3 单文件 | `backend/db.py`，库文件 `<项目根>/data/carpool.db` |
| 路径覆盖 | 便于测试隔离 | 环境变量 `CARPOOL_DB`；测试用临时库即靠它 |
| 缓存层 | 去掉 Redis | 内存 `TASKS`（读路径一级）+ SQLite（持久化下层） |
| polyline | 存表字段 | `vehicle_route.polyline` TEXT（JSON），不进 OSS |
| user 表 | 整表删除 | V1.0 不做登录，多用户隔离留 V2.0 |

类型按 A7 决策映射：`bigint → INTEGER`、`decimal(10,2) → REAL`、
`datetime → TEXT`（ISO8601 带时区偏移）、`json → TEXT`（`json.dumps`）。

### 2.2 表结构（8 张）

| 表 | 作用 | V1.1 相对原设计的调整 |
|---|---|---|
| `carpool_task` | 任务主体 + 目的地 + 模式 + 预算 | 新增 `task_name`；`status` 用 5 态 |
| `passenger` | 提交名单与解析状态 | — |
| `map_matrix` | 点到点距离/时间缓存 | **键改为「点对」，跨任务复用**（见 2.4） |
| `optimization_job` | 求解作业 + 8 态状态 | 新增 `lower_bound` / `stop_reason`（扩展列） |
| `solution` | 最终方案汇总 | `version=3` 表示最终方案 |
| `vehicle_route` | 每车路线 + 折线 | **新增 `coordinates` / `leg_durations`**（见 2.5） |
| `route_passenger` | 每人分摊明细 | 落 A1 的全部个人明细字段 |
| `algorithm_log` | 收敛快照 | — |

`candidate_route`（A5「Top-K 候选池」）**未建表**——A5 本身未实现，
建一张空表只会制造「看起来支持」的错觉。

### 2.3 并发模型：线程本地连接 + WAL

FastAPI 的 `BackgroundTasks` 在**线程池**里跑 `run_optimization`，
而接口在**事件循环线程**读同一个库，天然是两个线程并发访问。因此：

- **每线程一个连接**（`threading.local`），绝不跨线程复用 Connection；
- `journal_mode=WAL` + `busy_timeout=10000` → 读写不互相阻塞，偶发写冲突自动重试；
- `synchronous=NORMAL`（WAL 下已足够安全，省掉每次 commit 的 fsync）。

### 2.4 矩阵缓存：键从 (task_id, 点) 改为「点对」

原设计把矩阵缓存绑定在任务上（`task_id` 维度），意味着**换个任务、同样的地址要重新调 API**。
本实现把唯一索引改为 `UNIQUE(provider, from_point, to_point)`，`task_id` 仅作溯源：

```sql
CREATE UNIQUE INDEX idx_matrix_pair ON map_matrix(provider, from_point, to_point);
```

坐标键用 **`"%.6f,%.6f"` 定点字符串**而非 REAL 做键，避免浮点比较带来的命中不确定性。
读取走 `matrix_lookup`（分块 IN 查询，每块 200 组，避开 SQLite 999 变量上限），
写入走 `INSERT ... ON CONFLICT DO UPDATE`（UPSERT）。

**实测收益**：跑完一次任务后库里有 42 个点对；用**同一批地址**再提交一次，
42 对**全部命中**，高德 API 请求数归零。

### 2.5 让「重启后恢复」无损：两处扩展列

设计文档只要求 `vehicle_route` 存 `polyline`（折线）。但只存折线，
重启后恢复出来的结果**画不出站点标记、也画不出时间线**——前端需要：

- `coordinates`（`[{lat,lng,name}]`）：站点圆圈与姓名标签；
- `leg_durations`（`[分钟,...]`）：每段耗时，时间线累加用。

故追加两列（同样落到 `optimization_job` 的 `lower_bound` / `stop_reason`）。
**实测恢复**（进程重启后 `GET /api/tasks/{id}`）：

```
task_status=COMPLETED   job_status=STOP_STABLE   gap=1.8516   lower_bound=47.55
result.job_status=STOP_STABLE   coordinates 6 项 / leg_durations 5 段 / path 577 点
乘客分摊明细齐全（每人 name / sequence_no / allocated_cost / ride_duration_s）
restored_from_db = true
```

### 2.6 老库升级：无迁移框架的就地补列

单机工具没有 Alembic 之类的迁移框架。若用户已经有一个不含新列的旧库，
`init_db()` 会在 `CREATE TABLE IF NOT EXISTS` 之后跑 `_migrate()`：
用 `PRAGMA table_info` 查已有列，缺则 `ALTER TABLE ADD COLUMN`（幂等、可反复执行）。

```python
_EXTRA_COLUMNS = {
    "vehicle_route":    {"coordinates": "TEXT", "leg_durations": "TEXT"},
    "optimization_job": {"lower_bound": "REAL", "stop_reason": "TEXT"},
}
```

### 2.7 「持久化失败不上抛」原则

`_execute()` / `_query()` 把异常一律**吞掉只打印**，不向上抛。
理由：磁盘满、库文件被占用、权限异常都不应让**优化主流程崩掉**——
用户的诉求是「算出拼车方案」，持久化是配套能力，不能反客为主。
`test_db.py` 中专有一条用例验证「写库失败时 `set_task_status` 不抛异常」。

## 3. A8：求解状态八态枚举

### 3.1 状态定义与触发条件

| 状态 | 含义 | 触发点 |
|---|---|---|
| `INIT` | 刚创建，准备矩阵 | `optimize()` 入口（矩阵构建开始） |
| `FEASIBLE` | 已找到第一个可行方案 | 初始解构建完成且满足硬约束 |
| `OPTIMIZING` | 优化进行中 | ALNS 启动 |
| `STOP_GAP` | gap ≤ 5% 提前结束 | `_maybe_stop` 判定（仅 cost 目标） |
| `STOP_TIMEOUT` | 预算用尽 | 主循环自然退出 |
| `STOP_STABLE` | 连续无改善 | `_maybe_stop` 判定（仅最后阶段） |
| `OPTIMAL` | gap = 0，已证明全局最优 | cost 目标且 `gap ≤ 1e-9` |
| `FAILED` | 未找到可行方案 | 结束时仍有路线超 5400s 硬约束 |

`INIT → FEASIBLE → OPTIMIZING` 是严格时序。注意 **FEASIBLE 是瞬时里程碑**：
初始解是纯计算、几乎不耗时，通常只在库里留下痕迹——客户端 2 秒轮询时多半已到 `OPTIMIZING`。

### 3.2 FAILED 的 sub_status 细分

| sub_status | 判据 | 含义 |
|---|---|---|
| `PROVEN_INFEASIBLE` | 存在某乘客**直达**耗时 > 5400s | 数学上不存在可行方案（连直达都超时） |
| `SEARCH_FAILED` | 上述不成立但搜索没搜到 | 预算内没找到，**不代表不存在**（可放宽约束重试） |

崩溃类异常（如 API 报错）**不填** sub_status——既不是数学不可行、也不是搜索失败，
设计文档允许该列为 null。

### 3.3 三层状态的分工

系统里存在三个不同粒度的状态，各有归属表，不混用：

| 层 | 字段 | 取值 | 归属 |
|---|---|---|---|
| 任务 | `carpool_task.status` | CREATED / MAPPING / OPTIMIZING / COMPLETED / FAILED | 5 态，业务视角 |
| 作业 | `optimization_job.status` | 上述 8 态 | 求解视角 |
| 作业细分 | `optimization_job.sub_status` | PROVEN_INFEASIBLE / SEARCH_FAILED | FAILED 细分 |

对旧客户端（含现有前端）的兼容：`LEGACY_STATUS` 把 8 态压回
`PENDING / RUNNING / DONE / FAILED`，`stage` 字段照旧，
**旧前端不改一行也能继续轮询**。

### 3.4 终止判据与「连续无改善」窗口

```python
GAP_STOP_PCT  = 0.05          # 设计文档 §十四
STABLE_S_RATIO = 0.2          # 300s 预算 → 60s 窗口，按预算缩放
STABLE_S_MIN   = 3.0          # 下限：10s 预算档
STABLE_S_MAX   = 60.0         # 上限
```

`stable_window(budget) = clamp(0.2×budget, 3s, 60s)`。
窗口**只作用于最后一个阶段**：`fewest_vehicles` 的两阶段搜索若在第 1 阶段
（定车数）就因「无改善」退出，第 2 阶段（同车数压费用）根本没机会跑。

### 3.5 费用下界（gap 的分母）

gap 需要一个**严格可信**的下界，故取两个各自可证明成立者的较大值：

1. **人均直达摊派界**：由三角不等式，车内任一乘客直达距离 ≤ 车里程，
   车内最多 capacity 人 ⇒ `Σ_v D_v ≥ (Σ_j d_j) / capacity`。
2. **按容量分组的 max 界**：任意一车里程 ≥ 车内最远乘客的直达距离，
   把乘客按直达距离降序排，第 i 组至少贡献第 `capacity·(i-1)+1` 大的值 ⇒
   `Σ_v D_v ≥ Σ_i d_(capacity·(i-1)+1)`。

再代入费用函数 `C = BASE_FEE·k + PER_KM·Σ max(D_v,km − 3, 0)`（对里程、车数均单调不减）。

下界**有意不含** 5400s 时长约束与 `max_vehicles` 约束——这两个约束只会让真实最优**更贵**，
对下界无影响（下界仍有效）。代价是**偏松**，见 §4。

### 3.6 顺带修复的真 bug：5400 秒硬约束可被违反

修 A8 时发现一处会使「承诺失效」的真缺陷：原实现里
**只有 `_best_insertion`（插入启发式）检查单车 5400s 时长**，
而初始解（DBSCAN + 2-opt，不过时长）与**最终返回结果**都不检查。
后果是散场模式实测返回过 **5984 秒 > 5400 秒**的路线，并被当作**成功方案**返回，
下游 `e2e_alloc.py` 的 dropoff 段因此报「子任务失败」。

修复：把「超时车按辆数计罚分」加入 `evaluate`，搜索才有动力把超时路线拆掉：

```python
over_dur = sum(1 for v in vehicles if v.duration_s > MAX_ROUTE_SECONDS)
pen = (over + over_dur) * INFEASIBLE_PENALTY
```

## 4. 必须如实记录的限制：下界偏松

**gap 在正常规模下偏大，导致 `STOP_GAP` 不会触发、`OPTIMAL` 实际不可达。**

实测（真实高德路网任务，取自 `data/carpool.db`）：

| 场景 | 费用 | 下界 | gap |
|---|---|---|---|
| 5 人 pickup（1 车） | 86.43 | 46.34 | **87%** |
| 5 人 dropoff（1 车） | 88.05 | 47.36 | **86%** |
| 6 人 pickup（2 车） | 114.88 | 46.34 | **148%** |
| 6 人 dropoff（2 车） | 135.60 | 47.55 | **185%** |
| 15 人 pickup（3 车） | 202.97 | 163.78 | **24%** |
| 15 人 pickup（3 车） | 214.03 | 163.78 | **31%** |

合成随机实例（Haversine 离线矩阵，3 种子）：

| n | gap 区间 |
|---|---|
| 15 | 56% ~ 82% |
| 30 | 61% ~ 69% |
| 45 | 37% ~ 51% |

**规律很反直觉但可解释**：gap 在**小实例**上最大（5~6 人 2 车时高达 185%），
在 15 人以上反而收窄到 ≤ 51%。两个叠加原因：

1. **下界隐含「近乎零绕路」假设。** 人均直达摊派界
   `Σ_v D_v ≥ (Σ_j d_j)/capacity` 把「车里程之和」压到「直达距离均值」的量级，
   而真实拼车的绕路使总里程远大于此。以 6 人 pickup 为例：下界 `s_lb ≈ 13.1 km`，
   真实方案两车合计 33.7 km（V01 26.5 + V02 7.2，≈ 2.6 倍），gap 由此产生。
2. **`k_min` 少算车数。** 6 人时 `k_min = ceil(6/6) = 1`，起步价只算 1 辆车（16 元），
   而受 5400s 约束真实解用了 2 车（32 元），下界又少了一块。

n=15 时 `capacity` 摊派被更多乘客稀释、且真实方案绕路比例下降，故 gap 收窄。

**结论与建议**：

- `STOP_GAP`（5% 阈值）在当前规模**不会触发**——GAP_STOP_PCT 已在代码中生效，
  但它是为「下界足够紧」的将来（如加入列生成式更强下界）预留的；
- `OPTIMAL` 同理**实际不可达**（测试用人工构造「下界顶到最优」才触发）；
- **实际起作用的提前终止是 `STOP_STABLE`**，其收益见 §5；
- 前端因此**如实展示 gap 数值**（`距理论下界 24%`）而非暗示「已接近最优」，
  文案用「距理论下界」不用「最优性差距」。

## 5. 提前终止 A/B 对照（`tests/a8_stop_ab.py`）

`STOP_STABLE` 天然是「省时间 ↔ 损质量」的取舍，必须量化：

- **对照 A**：关闭提前终止（`stable_s=inf, gap_stop_pct=-1`）→ 一定跑满预算；
- **对照 B**：默认（`stable_window` + gap 5%）；
- 同一 `rng_seed` 下 **B 的迭代序列是 A 的前缀**，Δcost 才是「提前终止的代价」
  而非两次随机游走的噪声。

> **完整档实测数据已落盘**：`backend/tests/a8_stop_ab_result.txt`（3 规模 × 2 预算 × 3 种子）。
> 下表为该结果的汇总。

| n | 预算 | 费用 A | 费用 B | Δ费用 | 耗时 A | 耗时 B | 耗时节省 | 提前终止 |
|---|---|---|---|---|---|---|---|---|
| 15 | 10s | 226.20 | 226.20 | **+0.00%** | 10.0s | 3.7s | −63% | 3/3 |
| 15 | 30s | 218.51 | 226.20 | **+3.52%** | 30.0s | 6.7s | −78% | 3/3 |
| 30 | 10s | 369.02 | 373.23 | +1.14% | 10.0s | 4.8s | −52% | 3/3 |
| 30 | 30s | 369.01 | 369.01 | **+0.00%** | 30.0s | 10.2s | −66% | 3/3 |
| 45 | 10s | 484.92 | 486.36 | +0.30% | 10.0s | 6.7s | −33% | 3/3 |
| 45 | 30s | 483.20 | 484.92 | +0.35% | 30.0s | 9.7s | −68% | 3/3 |

**平均费用差 +0.89%，中位数 +0.33%，平均耗时节省约 60%；18/18 全部提前收敛。**

读法与结论：

- **短预算（10s）几乎零代价**：n=15 时 Δ=0.00%，n=30/45 也在 1.2% 以内。
  说明 3 秒窗口在短预算下正好卡在「已有收敛、再跑也难改善」的点上。
- **长预算（30s）会出现代价，但仅在一个组合上明显**：n=15 / 30s / seed=3 单例 +11.04%，
  把该组合均值抬到 +3.52%。其余 5 个组合的均值都 ≤ 1.14%。
  含义是：**小实例 + 长预算**时 ALNS 确实还有提升空间，此时 20% 预算的稳定窗口偏激进。
- **n=45 更稳**（Δ ≤ 0.35%）：规模大时单次迭代的边际收益本就低，提前停损代价小。

**调参结论**：默认窗口 `clamp(0.2×budget, 3s, 60s)` 在**生产默认预算（300s → 窗口 60s）**
下是保守的（窗口占预算比仅 20%，远小于实测「收敛后 60%+ 时间被浪费」的冗余量），
可放心开启。若后续面向「小实例 + 大预算」场景，可按规模把 `STABLE_S_RATIO` 调大
（如小实例用 0.35），把质量换回来。

# 拼车路线优化系统技术方案设计 V1.1

文档性质：系统架构与算法技术方案

基于《拼车路线优化系统业务需求规格 V1.1》，设计一个支持多人、多车型、多约束条件下的拼车路线优化系统。

系统目标：

在满足：

- 每位乘客必须被接送
- 单车容量约束
- 单车90分钟约束
- 地图路线有效性

的前提下：

寻找总费用最低的拼车方案。

V1.0 主要面向：

- 30人以内拼车任务
- 单终点
- 4人与6人车型混合
- 百度地图标准驾车路线

# 十一、费用尾差处理

确定性规则（V1.1 与业务需求对齐）：

规则：
本车费用先按全精度除以同乘人数，得到每人精确分摊值；展示时统一四舍五入到 2 位小数；四舍五入后产生的尾差（通常 1 分）**由本车接人顺序排在第一位的乘客承担**。

例如：
车费 100 元，3 人，每人精确分摊 33.3333…
展示：
- 接人顺序第 1 位：33.34（承担尾差 +0.01）
- 接人顺序第 2 位：33.33
- 接人顺序第 3 位：33.33

接人顺序以**最终地图复核后的顺序**为准，不在 ALNS 中间迭代步骤确定，避免方案变化导致尾差承担者跳动。

优势：
- 可复现
- 可审计
- 与司机/乘客认知一致（第一个上车的人多付 1 分）
- 同一方案重复运行结果完全一致

# 十三、求解状态设计


# 十三、求解状态设计

状态（8 种，V1.1 全量）：

```text
INIT
阶段 0：正在获取地图数据/生成矩阵

FEASIBLE
阶段 1：已找到第一个可行方案（优化中）

OPTIMIZING
阶段 2：ALNS 优化进行中

STOP_GAP
gap ≤ 5% 提前结束

STOP_TIMEOUT
阶段 2 总预算 300 秒用尽

STOP_STABLE
连续 60 秒无改善

OPTIMAL
gap=0，已证明全局最优

FAILED
未找到可行方案，需进一步看 sub_status：
  - PROVEN_INFEASIBLE：数学上已证明不可行（如多人直达超时）
  - SEARCH_FAILED：搜索预算内未找到，不代表数学上不存在
```

# 十八、V1.1 架构调整（重要）

## 1. 数据库：MySQL + Redis → 单机 SQLite 3

V1.1 不再使用 MySQL 和 Redis。理由：
- V1.0 定位为单机工具，不做多用户 SaaS；
- SQLite 3 是文件型数据库，随项目目录走，零部署；
- 矩阵缓存、优化中间状态直接放 Python 内存 dict，进程结束后持久化到 SQLite；
- polyline 直接存 SQLite TEXT 字段，不用 OSS/MinIO。

字段类型映射：
- MySQL `bigint` → SQLite `INTEGER`
- MySQL `decimal(10,2)` → SQLite `REAL`
- MySQL `datetime` → SQLite `TEXT`（ISO8601 字符串）
- MySQL `json` → SQLite `TEXT`（Python `json.dumps`）

## 2. 算法服务：独立部署 → FastAPI 同进程

V1.1 不拆分算法服务。理由：
- 单机工具，FastAPI 进程内直接调用 Python 算法模块；
- 用 FastAPI BackgroundTasks 异步跑优化，避免阻塞 HTTP worker；
- 并发优化任务数限制为 CPU 核数 - 2（留核给 API），超了排队。

## 3. WebSocket 推送字段扩展（V1.1）

等待页需要实时显示候选路线数、当前最佳费用、迭代次数、当前阶段、预计剩余时间。消息体从 `{type, value}` 扩展为：

```json
{
  "type": "stage" | "progress" | "best_cost" | "candidate_count" | "eta",
  "stage": "INIT" | "FEASIBLE" | "OPTIMIZING",
  "progress": 60,
  "best_cost": 520.5,
  "iteration": 350,
  "candidate_count": 520,
  "eta_seconds": 30,
  "timestamp": "2026-10-12T15:30:00"
}
```

## 4. 百度地图 AK 运维（V1.1 新增）

- AK 配置在环境变量 `BAIDU_MAP_AK`，不写进代码或数据库；
- 每日配额计数存在 SQLite `quota_usage` 表，按接口分（geocoding / direction / directionmatrix）；
- 单次请求失败重试 3 次，指数退避（1s → 2s → 4s）；
- QPS 超限（百度返回 429 或特定错误码）时退避 5 秒再试；
- 当日免费配额用尽时，暂停新任务，前端提示"地图配额已用完，明日再试或购买配额"；
- 地图失败时禁止把 distance/duration 当作 0，必须标记 MAP_ERROR 并在结果中说明。

## 5. 任务队列（V1.1 简化）

不引入 Celery/RQ。直接用：
- FastAPI BackgroundTasks 跑优化；
- SQLite `optimization_job` 表记录任务状态；
- 同时运行的优化任务数 ≤ max(1, CPU核数 - 2)；
- 超过的任务状态置为 QUEUED，前端显示"排队中"。

## 6. 三种优化模式的评价函数

V1.1 开放三种模式，评价函数见业务需求规格 V1.1。算法层通过统一的 `score(solution, mode)` 接口屏蔽差异：
- `cost`：字典序 (total_cost, total_duration, vehicle_count)
- `fewest_vehicles`：字典序 (vehicle_count, total_cost, total_duration)
- `balanced`：0.5×cost_norm + 0.3×time_norm + 0.2×vehicle_norm

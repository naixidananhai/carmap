# A1 费用分摊与个人乘车明细 · 实现说明

> 状态：**已实现并验证**（2026-10-14）
> 决策依据：《P0 冲突统一决策 V1.1》A1、《技术方案设计 V1.1》第十一节、《业务需求规格 V1.1》第五节
> 影响文件：`backend/optimizer.py`、`backend/main.py`、`frontend/index.html`
> 验证：`backend/tests/test_cost_alloc.py`（单元）、`backend/tests/e2e_alloc.py`（端到端不变式）、`backend/tests/e2e_frontend.py`

---

## 1. 为什么做这一项

P1 验证收尾后，对照 v1.1 设计文档做了一次覆盖度盘点，发现系统输出停在**整车费用**这一层：
`VehicleOut` 有 `passenger_count`、`order`（顺序）、`leg_durations`（每段耗时），
但**没有按人拆分的金额**，也没有**个人实际乘车时长**。

而拼车的产出物恰恰就是「每个人该付多少钱、坐了多久」——前端产品设计里明写的
「您的分摊费用：32.5 元」在后端完全没有支撑。这属于产品价值闭环的最后一公里，
且是已拍板（A1）却未落地的欠债。

实现成本低、零算法风险：纯展示层计算，不触碰已验证过的 ALNS / 2-opt / DBSCAN 链路。

## 2. 落地口径

### 2.1 费用分摊（`optimizer.allocate_cost`）

严格按《技术方案设计 V1.1》第十一节：

1. 本车费用按**全精度**除以同乘人数，得到每人精确分摊值；
2. 展示时统一**四舍五入到 2 位小数**；
3. 四舍五入产生的**尾差由接人顺序排在第一位的乘客承担**。

```
100 元 / 3 人  → [33.34, 33.33, 33.33]        第一位承担 +0.01
 16 元 / 6 人  → [2.65, 2.67, 2.67, 2.67, 2.67, 2.67]   第一位承担 −0.02
```

**尾差可为负。** 16/6 = 2.6667，各自四舍五入得 2.67，6×2.67 = 16.02 比车费多 0.02，
按同一条规则这笔偏差仍由第一位承担，故第一位为 2.65。规则要求的是"第一位承担全部
舍入偏差"，而非"第一位一定多付"。

**金额守恒不变式**：`sum(分摊) ≡ round(车费, 2)`，2 万组随机用例零违反。
分摊既不凭空多收，也不会少收。

### 2.2 个人乘车时间（`ride_duration`）

按《业务需求规格 V1.1》第 156 行：

> 乘客 i 的 t_ride(i) = 从其上车点到终点的逐段地图时间累加（不是整车总时间）

**两种模式的累加方向相反**，这是实现时最容易出错的地方：

| 模式 | 乘客在哪上车 | 累加方向 | 公式（`leg_secs[k] = stops[k] → stops[k+1]`） |
|---|---|---|---|
| 集合（pickup） | 各自的家 | 从上车点向终点 | `ride(i) = sum(leg_secs[i:])` |
| 散场（dropoff） | **活动点（同时上车）** | 从活动点向自己下车点 | `ride(i) = sum(leg_secs[:i])` |

散场模式下车队路线为 `活动点 → h₀ → h₁ → …`，所有人在活动点同时上车，
因此**越晚被送达、乘车越久**；集合模式则相反，**越晚上车、乘得越短**。

以路线 `A→B→C→终点` 为例共有 3 段，集合模式下乘客 B（下标 1）
`ride = leg[1] + leg[2] = B→C→终点`，与设计文档口径逐字一致。

### 2.3 直达时间（`direct_duration`）

取**物理方向**的正向矩阵，不取转置后的矩阵：

- 集合：`家 → 活动点`
- 散场：`活动点 → 家`

散场模式虽然为矩阵做了转置（用于寻优），但个人明细展示的是乘客的真实体验，
必须用转置前的 `fwd_matrix`；仅当矩阵降级为 Haversine（对称）时才回退到 `dm.get()`。

### 2.4 绕路预警（`detour_warning`）

按《业务需求规格 V1.1》第 59 / 280 行，满足任一即标注 `DETOUR_WARNING`：

- 实际乘车时长 **> 80 分钟**（4800 秒），或
- 绕行比例 `ride / direct` **> 1.3**

`direct = 0`（乘客与活动点重合）时比例无定义，不因除零误报。
预警**仅提示、不阻断方案**，与设计一致。

## 3. 一处设计文档未覆盖的口径：散场模式的「第一位」

A1 原文的表述是「**第一个上车的人**多付 1 分」。这在集合模式下没有歧义，
但**散场模式下所有乘客在活动点同时上车，不存在"上车顺序"**，规则无从落地。

采用的解释：

> `sequence_no` 统一取**沿最终路线的访问顺序**（1 起）——
> 集合模式下即上车顺序，散场模式下即**送达顺序**；
> 尾差一律由 `sequence_no == 1` 的乘客承担。

理由：确定性、可复现、可审计（与设计文档强调的三条性质一致），
且与前端实际展示的顺序一致（前端展示的 `order` 在散场模式下就是送达顺序）。
**这是本实现对设计文档的补充解释，建议回写进《技术方案设计》第十一节。**

## 4. 接口改动

`VehicleOut` 新增 `passengers` 字段（与该车 `order` 同序），元素为 `PassengerDetailOut`：

| 字段 | 类型 | 说明 | 对应 `route_passenger` 设计字段 |
|---|---|---|---|
| `name` | str | 乘客姓名 | — |
| `sequence_no` | int | 沿路线访问顺序（1 起） | `sequence_no` |
| `direct_duration_s` | int | 起点直达终点秒数 | `direct_duration` |
| `ride_duration_s` | int | 从本上车点到终点的实际乘车秒数 | `ride_duration` |
| `increase_duration_s` | int | `ride − direct` | `increase_duration` |
| `detour_ratio` | float? | `ride / direct`，`direct = 0` 时为 `null` | `detour_ratio` |
| `allocated_cost` | float | 本车分摊金额（**已含尾差**） | `allocated_cost` |
| `warning` | str? | `DETOUR_WARNING` / `null` | `warning` |

**命名差异说明**：设计文档的 `direct_duration` 等字段是**整数秒**，而本响应中既有的
`leg_durations` 是**分钟（float）**。为避免同一响应里出现单位歧义，个人明细的时长字段
统一加 `_s` 后缀并明确为整数秒；后续接入 SQLite（A7）时直接映射即可。

前端同步改动：

- 每辆车卡片内新增分摊明细表（顺序 / 姓名 / 分摊 / 实际乘车 / 较直达 / 绕路预警）+ 车费脚注；
- 「复制结果」文本补充每人分摊与乘车时长；
- CSV 导出新增 `分摊元 / 个人乘车分钟 / 直达分钟 / 较直达分钟 / 绕行比例 / 绕路预警` 六列；
  乘客允许重名，导出时按出现顺序用队列一一对应，避免错配。

## 5. 验证

### 5.1 单元测试 `tests/test_cost_alloc.py`（全部通过）

- 设计文档样例 `100/3 → [33.34, 33.33, 33.33]` 精确命中；
- **2 万组随机用例**验证金额守恒不变式，零违反；
- 尾差为负的场景（`16/6`）符合"第一位承担全部舍入偏差"；
- 边界：1 人 / 整除 / 极小金额 `0.01 元` / 0 人；
- 绕路预警阈值：80 分钟边界、比例 1.3 边界、`direct = 0` 不除零。

### 5.2 端到端不变式 `tests/e2e_alloc.py`（全部通过）

集合 / 散场各跑一个 6 人任务，逐车校验 8 类不变式：明细条数与姓名顺序、
`sequence_no` 连续、分摊合计 == 车费、`increase ≡ ride − direct`、
`detour_ratio` 一致、乘车时长沿路线单调（集合递减 / 散场递增，且首末位增量为 0）、
乘车时长 ≤ 整车时长、warning 与阈值规则一致。

## 6. 顺带修复：e2e_frontend 的测试卫生缺陷

验证过程中发现 `e2e_frontend.py` 存在会造成**假失败**的 harness 缺陷，已一并修复：

- **现象**：「活动点已设为郑州东站」间歇性失败，报告坐标为地址检索的返回值而非默认值。
- **根因**：脚本用**固定调试端口 9333** 且退出时只 `proc.terminate()`。Edge 会派生
  gpu/renderer/network 等子进程，启动进程又常退化为 launcher，导致**整棵进程树未被清理**、
  残留进程继续占着 9333。下一轮新 Edge 抢不到该端口，`cdp_capture` 便连上了
  **上一轮遗留实例的陈旧页面**——那页早已跑完第 4 节，`destPoint` 已被检索结果覆盖。
- **修复**：
  1. 调试端口改为**每次运行取空闲端口**，杜绝端口碰撞；
  2. 收尾时 `taskkill /T /F` 之外，再按 **profile 目录匹配兜底清理** Edge 进程；
  3. 新增「连到的是全新加载的页面」守卫（检查 `currentResult` 为空、`destPoint` 为默认值），
     一旦连上陈旧页面立即中止并明确报错，避免后续断言出现难以定位的误报。
- **验证**：修复后连续 3 次运行均 29/29，且退出后残留进程 0、端口已释放。

此缺陷与 A1 功能无关，属既有测试代码问题，但会掩盖真实回归，故一并处理。

| 项 | 设置 |

## 1. 结论一：ALNS 有真实收益，约 −48%

### 1.1 四组对照（15 实例均值，cost 模式）

| 求解器 | 平均费用 | 平均车数 | 相对上一档 |
|---|---:|---:|---:|
| 每人单独叫车（业务基准） | 1224.02 元 | 28.5 | — |
| DBSCAN 初始解（生产路径起点） | 699.97 元 | 16.5 | −42.8% |
| 单点起车 + 最便宜插入（0 迭代） | 708.41 元 | 6.1 | +1.2% |
| **+ ALNS** | **366.11 元** | **5.7** | **−47.7%** |

**ALNS 相对生产初始解 −47.7%；相对等价构造启发式 −48.3%。**
即：ALNS 的收益无法被"换个更好的构造解"替代——构造解只能到 700 元档，ALNS 直接压到 366 元档。

### 1.2 三种模式的收益

| 模式 | 贪心单点 | DBSCAN 初始 | +ALNS | ALNS vs 初始 | ALNS vs 贪心 |
|---|---:|---:|---:|---:|---:|
| cost | 708.41 | 699.97 | 366.11 | −47.7% | −48.3% |
| balanced | 0.38 | 0.46 | 0.22 | −53.1% | −43.2% |
| fewest_vehicles | 6.07 | 16.47 | 5.67 | −65.6% | −6.6% |

> `fewest_vehicles` 相对贪心只有 −6.6%，因为"车数"这个指标构造解已经能做到 6.07 辆（容量下限 ceil(n/6)）。它的主要成绩来自修正 DBSCAN 初始解的 16.47 辆，而非自身搜索能力。

### 1.3 真实高德矩阵交叉验证（24 人，0 空洞）

| 模式 | 贪心单点 | DBSCAN 初始（车数） | +ALNS（车数） |
|---|---:|---:|---:|
| cost | 688.17 | 745.32（18 车） | **341.22（4 车）** |
| fewest_vehicles | 5.00 | 18.00（18 车） | **4.00（4 车）** |

真实路网结论一致：**−54% 费用，18 车 → 4 车**。

## 2. 结论二：ALNS 不依赖初始解质量

同一实例、同一预算，仅更换初始解种子：

| 模式 | S1：DBSCAN 种子 + ALNS | S2：单点贪心种子 + ALNS | S2/S1 | 终车数 |
|---|---:|---:|---:|---:|
| cost | 360.73 | 366.90 | 101.7% | 5.73 / 5.80 |
| balanced | 0.212 | 0.215 | 101.4% | 5.73 / 5.80 |
| fewest_vehicles | 5.667 | 5.667 | 100.0% | 5.67 / 5.67 |

从 **16.5 辆车**或从 **n 辆单点车**出发，终值差异 < 2%（落在噪声内），终车数一致。
→ **ALNS 是"自愈"的**：初始解只要不太离谱，终值几乎不受影响。这解释了为什么第 1 节中两条完全不同的构造基线都被收敛到同一档次。

## 3. 结论三：「退火失效」假设——数值失配成立，但未造成损失

### 3.1 失配证据（实测）

| 模式 | T0 | T 末（4s） | 迭代数 | 劣解被接受 | 劣解接受率 |
|---|---:|---:|---:|---:|---:|
| cost | 63.6–81.6 元 | 31.5–56.8 元 | 725–1407 | 294–672 | **38.0%–47.8%** |
| balanced | 0.034–0.064 | 2.3e-2 – 3.2e-2 | 826–1380 | 436–524 | 35.7%–52.8% |
| fewest_vehicles | 10.0 | 4.9–6.9 | 756–1432 | 17–111 | 1.5%–10.0% |

- **温度量纲错配**：cost 模式 T0 ≈ 63–82 元，而单步费用变化 |Δ| 量级只有 10–13 元，Δ/T ≈ 0.16 → 接受概率约 85%，实测劣解接受率 38%–48%。
- **退火永不冷却**：α = 0.9995，4 秒内只跑 725–1432 次迭代，T 仅衰减到 T0 的 37%–73%。要让 T 降两个数量级需要约 9200 次迭代——**在设计预算内退火只有"恒温"阶段，没有"冷却"阶段**。

### 3.2 但温度取值不敏感（6 实例扫描，cost 模式）

| 变体 | 均值 | | 变体 | 均值 |
|---|---:|---|---|---:|
| T0 = 0.01·s0 | 272.08 | | auto 默认 0.1·s0 | 275.78 |
| α = 0.999 | 272.26 | | α = 0.9995（默认） | 278.57 |
| T0 = 0.5·s0 | 273.14 | | **T0 = 0（纯爬山）** | **281.75** |
| T0 = 0.002·s0 | 273.29 | | α = 1（恒温） | 283.23 |
| T0 = 0.05·s0 | 273.41 | | α = 0.9999 | 284.10 |

极差 4.3%（272.1–284.1），**统计上不显著**。唯一明确信号是 **T0 = 0（拒绝一切劣解）最差**。

### 3.3 判定

| 判断 | 结论 |
|---|---|
| 「T0 = best_score[0] × 0.1 与 δ 量纲失配」 | ✅ **成立**（Δ/T ≈ 0.16，接受率 38–48%） |
| 「退火调度在预算内不冷却」 | ✅ **成立**（T 只降 40%） |
| 「因此损失了优化质量」 | ❌ **不成立**。温度扫描全区间差异在噪声内 |
| 「应该拆掉接受门做纯爬山」 | ❌ **反例**：T0=0 反而最差（281.75） |

**根因**：真正的搜索驱动力是 destroy + repair（泛化插入）本身，模拟退火门只决定 current 状态怎么走动。门开着能避免过早锁死在局部最优，但它"开多大"无关紧要。

### 3.4 一处实现脆弱点（建议修但不紧急）

```python
self.T0 = self.best_score[0] * 0.1 if isinstance(self.best_score[0], float) else 10.0
```

用 Python 的运行时类型来判断温度量纲，导致三种模式落到三个互不相关的尺度：
- cost：`total_cost` 是 float → T0 ≈ 63–82
- balanced：`score` 是 [0,1] 的 float → T0 ≈ 0.04
- fewest_vehicles：`vehicle_count` 是 int → 落入 `else` 分支 → T0 = 10.0

这是"意外正确"，不是设计。建议改为按模式显式给定相对尺度。

## 4. 结论四：A3 —— 三种模式中只有 cost 有独立价值

### 4.1 同一实例交叉对比（15 实例均值）

| 模式 | 平均费用 | 平均车数 | 相对 cost |
|---|---:|---:|---:|
| cost | 366.11 元 | 5.73 | — |
| balanced | 369.79 元 | 5.73 | **+1.00%** |
| fewest_vehicles | 404.87 元 | 5.67 | **+10.59%** |

**三种模式在 14/15 个实例上给出完全相同的车数。**

### 4.2 逐实例（节选）

| 实例 | cost 费用 / 车 | balanced 费用 / 车 | fewest 费用 / 车 |
|---|---|---|---|
| n20_s1 | 239.83 / 4 | 268.73 / 4 | 261.88 / 4 |
| n30_s3 | 359.80 / **6** | 362.81 / 5 | 366.24 / **5** |
| n45_s2 | 498.82 / 8 | 498.79 / 8 | **616.86** / 8 |
| n45_s3 | 498.15 / 8 | 520.59 / 8 | **601.86** / 8 |

### 4.3 归因

**balanced 为什么冗余**：`score = 0.5·cost_norm + 0.3·time_norm + 0.2·vehicle_norm`，其中
`time_norm = 总时长/(n×5400)`、`vehicle_norm = 车数/n` 的分母极大（如 20 人实例中 time_norm ≈ 0.089、vehicle_norm = 0.2），而 `cost_norm = 费用/基准 ≈ 0.43`。
代入权重后 **cost 项占最终 score 的约 76%** → balanced 在数学上就是 cost 模式的弱化复制品。

**fewest_vehicles 为什么是反向劣势**：费用函数 `C(D) = 16 + 3·max(D_km − 3, 0)` 中，**16 元/车的起步费本身已强烈激励并车**。因此 cost 模式会自发收敛到容量下限 ceil(n/6)：n=20→4 车、n=30→5 车、n=45→8 车，与 fewest_vehicles 的 5.67 车几乎一致。既然车数已经被 cost 模式拿到下限，fewest_vehicles 就只剩"为了车数牺牲费用"的副作用（+10.6%，最坏 +23.7%）。

### 4.4 对 A3 的建议

| 模式 | 建议 | 理由 |
|---|---|---|
| `cost` | **保留** | 唯一有独立优化价值的模式；且天然达到最少车数 |
| `balanced` | **删除** | 与 cost 无系统差异（+1.0%），权重设计使 cost 项主导，属冗余模式 |
| `fewest_vehicles` | **改写** | 现状与 cost 车数相同却贵 10.6%。真正的产品需求是「**车数上限 K 的硬约束 + 最小费用**」（对应 A2 车型拆分），而非一个完整的优化模式 |

## 5. 结论五：算力边际收益陡峭递减 —— 时间预算应下调

### 5.1 预算扫描（cost 模式）

| 预算 | n≤30（6 实例） | n=30 s1 | n=45 s1 / s2 / s3 |
|---|---:|---:|---|
| 1s | 272.17 | — | — |
| 3s | 273.64 | — | — |
| 4s | — | 382.91（5 车） | 476.98 / 497.11 / 506.05 |
| 10s | 273.53 | — | — |
| 20s | 276.11 | — | — |
| 60s | — | 335.67（6 车） | 457.23 / 494.33 / 495.54 |

- **n ≤ 30：1 秒后质量即饱和**，1s/3s/10s/20s 得分 272.2 / 273.6 / 273.5 / 276.1，继续跑不升反降（在多局部最优间随机跳动）。

### 5.2 已执行的改动

对 n≤30 常见的活动场景，用户等待时间从 60 秒降到 10 秒，质量零损失；需要极致省钱的用户仍可手动调高。

## 6. 附带发现：初始解存在结构性缺陷

`build_initial_solution` 中，**每个 DBSCAN 噪声点都被单独开一辆车**：

```python
for i in noise:
    vehicle_indices.append([i])     # ← 噪声点 = 独立一车
```

在 `eps_km=2.0`、乘客抖动 ±2.2km 的条件下，**平均 16.5 辆车 / 28.5 人**（合理值约 5 辆），甚至出现 21 辆车 / 45 人的情况。

- 对**最终质量无影响**（结论二已证明 ALNS 能自愈）
- 但对**过程指标有害**：进度条中间态显示离谱车数；ALNS 前期大量迭代被消耗在"把 16 辆车并回 5 辆"上
- 修复代价极低：噪声点应合并到最近的有余量车辆，而非独立成车

# 第二部分：改造实施与复测

## 9. 落地的改造

### 9.1 退火调度：T0 显式化 + 按时间冷却

**改动**：
- `T0` 不再用 `isinstance(score[0], float)` 猜量纲，改为按模式显式给定：
  `cost` → `0.1 × 初始费用`（单步 δ≈0.03×总分 ⇒ Δ/T≈0.15~0.3）；`fewest_vehicles` → `10.0`（单步 δ=1 辆）
- 降温由「按迭代 `α=0.9995`」改为「**按时间几何降温**」：`T = T0 · T_end_ratio^(elapsed/budget)`，
  默认 `T_end_ratio = 0.35`（取自 P1 实测：旧调度在 4s 预算下恰好衰减到 T0 的 37%~73%）

**为什么要改**：旧调度在长预算下失控——60 秒约 2.5 万次迭代，`0.9995^25546 ≈ 3e-6`，
**T 在预算前 30% 就崩到接近 0，退火退化为纯爬山**（而 P1 §3.3 已实测纯爬山是最差变体）。
实测 `T末/T0`：60s 下为 **6.88e-09 / 1.93e-05 / 4.11e-05**，确认退火完全失效。

**A/B 结果**（cost 模式）：

| 场景 | 新的按时间降温 | 旧的按迭代降温 | 差异 |
|---|---:|---:|---:|
| 4s（9 实例均值） | 375.57 元 | 374.45 元 | +0.53%（噪声内） |
| 60s（3 实例均值） | **437.48 元** | 443.41 元 | **−1.34%** |

**如实结论**：这是一次**正确性修复，不是性能优化**。实测中性偏正向（短预算在噪声内，长预算略好）。
收益在于「退火曲线在任何预算下都真实走完」，行为可预测、与预算无关。

### 9.2 fewest_vehicles 改为两阶段

**改动**：`fewest_vehicles` 拆成两阶段——
阶段 1（40% 预算）用「车数优先」目标定出最少车数；阶段 2（剩余 60%）以阶段 1 最优解为起点，
在「车数 ≤ 该值」的**硬约束**下最小化费用。

**复测**（9 个标准实例 × 3 个随机种子 = 27 次运行）：

| 配置 | 平均费用 | 平均车数 | 相对 cost |
|---|---:|---:|---:|
| A `cost` | 373.58 元 | 5.70 | — |
| B `fewest_vehicles` 两阶段（新） | **382.33 元** | 5.67 | **+2.34%** |
| C `fewest_vehicles` 单阶段（旧行为） | 416.56 元 | 5.67 | +11.50% |

**两阶段相对单阶段 −8.22%**；相对 `cost` 的费用劣势从改造前的 **+10.59% 压到 +2.34%**，车数不变（5.67）。

### 9.3 删除 `balanced` 模式

`cost / balanced / fewest_vehicles` → **`cost` + `fewest_vehicles`**。
- `optimizer.evaluate` 移除加权和分支
- `main.py` 增加 `normalize_mode()`：旧客户端传 `balanced` 时**静默映射为 cost 并打日志**（已验证：返回正常结果 2 车 / 114.88 元）；未知值回退 `cost`
- 前端 `index.html` 移除「时间均衡」选项并加提示
- 顺带修正了前端「求解预算」的说明文案（"60 秒后收益递减" → "10 秒后收益递减"）

### 9.4 初始解：噪声点不再单独成车

`build_initial_solution` 中噪声点改为按「插入后里程增量最小」并入有余量的既有车辆，无处可插才单点成车。

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 初始解平均车数 | 16.47 车 | **7.33 车** |
| 初始解平均费用（15 实例） | 699.97 元 | **464.88 元** |
| 初始解 / 每人单独叫车 | 57.2% | **38.0%** |

### 9.5 新增「车数上限」硬约束

- `evaluate(..., max_vehicles=K)`：超出一辆即在首元素加罚分，使超约束解永不优于任何合理解
- `optimize(..., max_vehicles=)` / `POST /api/tasks` 的 `max_vehicles` 字段 / 前端「车辆上限（可选）」输入框
- 上限低于满载下限 `ceil(n/6)` 时自动上调，并通过结果里的 `warning` 字段如实告知
  （已验证：12 人 + `max_vehicles=1` → 上调为 2 辆，返回 `warning: 车数上限 1 辆低于满载下限，已按 2 辆计算`）
- **约束严格遵守：分散实例 18 组测试，违反 0 次**

## 10. 改造中发现并修复的两个真 bug

### Bug 1：T0 被硬约束罚分污染

引入 `max_vehicles` 后，若**初始解本身违反上限**，`best_score[0]` 里含着 `1e6` 罚分，
而 T0 由 `score[0] × 0.1` 推导 → **T0 被算成 1e5 量级，退火立刻退化为随机游走**。
**修复**：温度改用「去掉罚分」的能量标定。

### Bug 2（更隐蔽）：满载时的搜索冻结 —— 导致 `fewest_vehicles` 一直在白跑

**现象**：某分散实例上 `cap=4`，跑 30 秒 / **23902 次迭代，0 次改进、0 次接受劣解**，
结果恒等于初始解（981.07 元）。

**根因**：当所有车都满载时（`n = 6k`、每车 6 人——**正是车数最优配置**），
`repair_greedy` 找不到任何有余量的车，只能给每个被移除的乘客新开一辆车
→ 候选车数必然上涨 → 在车数优先目标或车数上限约束下被拒绝
→ **每一次迭代都被拒绝，搜索彻底冻结**。

**这解释了 §4 的老问题**：旧 `fewest_vehicles` 车型达到下限后费用偏高 10.6%，并非"字典序设计错"，
而是**它到达车数下限的那一刻就冻结了**。

**修复**：把「用于排序的字典序分数」和「用于退火接受判断的能量」分开——
接受门只看真实费用（允许 current 在超限状态间穿行），best 仍按含罚分的字典序追踪，
因此**返回的解一定是可行解**。这一改动对无约束场景是**逐位等价**的（energy ≡ score[0]）。

修复后同实例：`cap=5` 从 692.15 元 → **545.74 元**（与自由求解 540.30 持平）。

## 11. 被回退的尝试（如实记录）

为解除 Bug 2 中 `cap = 容量下限` 这一极端场景的冻结，曾实现两个算子并实测：

| 算子 | 作用 |
|---|---|
| 换出链（ejection chain） | 满载车也能插入：换出车内一人重新安置，链长有界 |
| 交换算子（swap） | 在等车数的解空间里对调两车之间的乘客 |

**实测结果（9 个标准实例，cost 模式）**：

| 配置 | 平均费用 | 每次运行平均迭代数 |
|---|---:|---:|
| 新算子开启 | 389.83 元 | 296 |
| 新算子关闭 | **371.95 元** | 4611 |

**净负面：质量差 +4.81%，迭代吞吐掉 15 倍，并且没有解除 `cap=容量下限` 的冻结。**

**决定：两个算子全部回退。** 结论是这两个 neighborhood 的收益远小于它挤占的迭代预算，
而"所有车恰好满载且地理高度分散"是一个很窄的病理场景，不值得用主场景 4.81% 的质量去换。

**遗留限制（如实记录）**：当 `max_vehicles` 恰好等于容量下限 `ceil(n/6)` **且**乘客高度分散时，
搜索可能停在初始解上（典型：24 人 / 4 车 / 上限 4 → 981.07 元，而放宽到 5 车为 540.30 元）。
18 组分散实例测试中只有 1 例出现该退化；其余用例上限未绑定或绑定后无损。

# A9 人均车费上限与「人工确认淘汰」实现说明

> 对应《P0 冲突统一决策 V1.1》新增项 **A9**。
> 代码：`backend/optimizer.py`（`per_capita_cost` / `split_excluded` / `subset_matrix` /
> `suggest_drops`）、`backend/main.py`、`backend/db.py`、`frontend/index.html`。
> 测试：`backend/tests/test_per_capita.py`（76 项）、`backend/tests/e2e_frontend.py`。
>
> **修订（2026-10-14，第二版）**：剔除主键由**姓名**改为**稳定 id**（修同名连坐缺陷，见 §3.0）；
> 前端人均上限由数字输入框改为**下拉选项**（不限 + ¥2 起、步进 ¥2）。

---

## 1. 业务口径（业务方确认，实现不得偏离）

| 编号 | 口径 | 实现含义 |
|---|---|---|
| **B1** | 人均车费 = **拼车总费用 ÷ 参与人数**，**乘客实付**，无平台补贴 | `per_capita_cost(total, served) = total / served`，无任何补贴项 |
| **B2** | 被剔除者**不再参加活动** | 既不产生成本，也**不计入分母**；不进方案、不进乘客表 |
| **B3** | 超限时**算法只给建议**，人工确认后才剔除 | 后端只产出 `drop_suggestion`；前端弹建议卡片，点「确认剔除并重算」才带 `exclude_ids` 重算 |
| **B4** | 剔除要**精确到人** | 主键是乘客**稳定 id**，不是姓名——同名乘客不能被连坐（见 §3.0） |

**B2 让本轮问题比上一轮讨论的版本干净得多。** 上一轮假设「被剔除者改为自行打车」，
于是必须比较「省下的拼车费 vs 他自费的成本」，结论是多数情况全社会更贵。
在 B2 语义下被剔除者根本不出行，这个比较不再需要——优化目标就是
**在尽可能多保留人的前提下，让剩下的人的人均 ≤ 上限**。

---

## 2. 为什么这个问题比看上去难

### 2.1 总费用是「车数」的阶梯函数

费用函数 `C(D) = 16 + 3·max(D_km − 3, 0)`，每辆车固定 16 元起步价。
实测（15 人实例）：

| 车数 | 总费用 |
|---|---|
| 1 车 | ¥77.62 |
| 2 车 | ¥154.90 |
| 3 车 | ¥212.78 |
| 4 车 | ¥367.36 |

**唯一的成本杠杆是车数。** 剔除一个人而车数不变时，分子几乎不动、分母 −1
→ 人均**必然上涨**（数学上：分子降幅只要小于 `C/n`，人均就上升；而 `C/n` 是人均值本身，
单剔一人通常只省几元，远小于它）。

### 2.2 实测：剔掉**最远**的人，总费用反而上升

15 人实例，剔掉距集合点最远的乘客11（20.8 km）：

```
3 车 ¥212.78 → 3 车 ¥222.66   人均 ¥14.19 → ¥15.90
```

剩下 14 人仍然需要 3 辆车，而且重新分组后路线更长。

### 2.3 人均随剔除人数呈 **U 形**（前缀扫描：只保留最近的 k 人）

| 保留 k 人 | 车数 | 总费用 | 人均 |
|---|---|---|---|
| 15 | 3 | ¥212.78 | ¥14.19 |
| 14 | 3 | ¥206.15 | ¥14.72 |
| 13 | 3 | ¥185.98 | ¥14.31 |
| **12** | **2** | **¥154.90** | **¥12.91 ← 最低** |
| 11 | 2 | ¥145.94 | ¥13.27 |
| 10 | 2 | ¥138.21 | ¥13.82 |
| 9 | 2 | ¥136.73 | ¥15.19 |
| 6 | 1 | ¥108.43 | ¥18.07 |
| 5 | 1 | ¥77.62 | ¥15.52 |
| 3 | 1 | ¥64.59 | ¥21.53 |

**最低点恰好落在「车数刚少一辆」的位置**（3 车 → 2 车）。剔太少没用（甚至涨），
剔太多反而回升（1 辆车由更少的人分摊）。

### 2.4 结论：**人均 10 元在本实例物理上不可达**

该实例人均最低 `¥12.91`（12 人 2 车）。要人均 ≤ 10 需总额 ≤ ¥150，
即 2 辆车平均每辆 ≤ ¥75（≈22.7 km），而实测每辆 ¥77.45（≈23.5 km）。
**仅靠剔人做不到**——这是空间分散度决定的，不是算法不够好。

机制本身不回避这一点：`achievable=false` 时会如实报告
「已验证的最省方案是剔除 N 人后人均 ¥X，仍高于上限」，并给出根因
（车均里程 gap）与整改建议（放宽上限 / 改用更集中的上车点）。

## 3. 实现

### 3.0 剔除主键：**稳定 id**（第二版修订）

**问题**：第一版用**姓名**当剔除主键。一批名单里出现两个「张伟」（现实中很常见）时，
剔一个会把两个都剔掉——另一个「张伟」凭空失去参加活动的资格，且通知里只写「剔除 张伟」，
当事人无法申辩。

**修复**：主键改为乘客的**稳定 id**，贯穿全链路：

| 层 | 落地方式 |
|---|---|
| 前端 | 每行分配 `p1` / `p2` / …（`pidSeq` 只增不减，删行**不回收、不重排**）；DOM 用 `data-pid` 定位而不是数组下标（顺带修掉「删行后 `passengers[i]` 写错行」的老 bug） |
| 请求 | `passengers[].id` 带上稳定 id；`exclude_ids: [str]` 是**唯一**剔除通道（不再有 `exclude_names`） |
| 后端 | `assign_passenger_ids()` 归一化：已传 id 原样保留；未传则按提交顺序回退 `P001/P002...`（兼容手工调 API）；**id 重复直接 400**（主键重复会让剔除连带误伤） |
| 建议 | `suggest_drops` 的整车剔除候选用 `p.id` 圈人；每项同时给 `drop_ids`（执行口径）与 `drop_names`（展示口径），两者同序一一对应 |
| 结果 | `PassengerDetailOut.passenger_id` / `coordinates[].passenger_id` 随方案返回，前端据此反查地址，不再靠姓名匹配 |
| 库 | `passenger.ext_id`、`route_passenger.passenger_ext_id`、`carpool_task.excluded_ids` 三列（`_EXTRA_COLUMNS` 老库自动补） |

为什么回退 id（`P001...`）也安全：前端「剔除并重算」提交的始终是**全量名单** + `exclude_ids`，
被剔者不会让后面的人往前顶，因此两次提交的位置 id 恒定对齐。

### 3.1 `optimizer.py`

| 函数 | 作用 |
|---|---|
| `per_capita_cost(total, served)` | 人均定义（0 人 / 负数 → `None`，不抛异常） |
| `split_excluded(passengers, exclude_ids)` | A9：按**稳定 id** 拆出「保留 / 被剔除」两组（B4 的落点） |
| `subset_matrix(dm, keep_idx, dest_idx)` | 从整张矩阵裁出「子集 + 终点」小方阵，**保留 provider 真实数据** |
| `_estimate_subset(...)` | 不跑 ALNS 的快速估算（直接用初始解的费用），用于候选排序 |
| `suggest_drops(...)` | 候选生成 → 估算排序 → 少量真实求解 → 排序取优 |

常量：`PER_CAPITA_MIN_SERVED = 2`（最低成团人数）、`PER_CAPITA_NEAR_PCT = 0.08`。

### 3.2 候选生成（两族，去重）

| 族 | 生成方式 | 数量 |
|---|---|---|
| **C1 距离前缀** | 按「家→活动点」距离降序，剔掉最远的 m 人（m = 1..n−min_served） | ≤ `max_candidates − 车数`，超限均匀抽样 |
| **C2 整车剔除** | 剔掉当前解中某辆车的**全部**乘客 | = 车数，**优先保留不抽样** |

C2 的存在理由见 §2.1：只有整车剔除才可能真正减一辆车、把总费用降下来。

### 3.3 两级求解（控制耗时）

1. **估算**：对每个候选调 `build_initial_solution`（DBSCAN + 容量拆分 + 2-opt）算费用，
   不跑 ALNS。微秒~毫秒级，可对几十个候选全估。
2. **真实求解**：只对 `verify_top` 个候选跑真正的 `optimize`。
   入选顺序 = 「估算达标的 2 个」+「估算最优的 1 个」+「**最保守的 1 个**」+ 其余。
   最保守候选必入选是硬性要求——只按估算人均排序会让「剔很多人」的极端方案
   （分母小 → 人均看着低）垄断验证名额。
   `verify_top` **下限 3**，默认 4。
   实际预算由调用方给：`max(1.0, min(3.0, time_budget_s / 10))`。

### 3.4 取优规则

```python
# 有达标候选 → 达标者中保留人数最多
if ok_list:
    best = max(ok_list, key=lambda c: c["keep_count"])
# 全不达标 → 「近似同优」带宽内保留人数最多
else:
    band = min(pc) * (1 + PER_CAPITA_NEAR_PCT)
    best = max([c for c in verified if c["per_capita"] <= band],
               key=lambda c: c["keep_count"])
```

**为什么不是「取人均最低」**：实测未达标时，人均最低的候选是「剔到只剩 2 人（¥13.39）」，
而「剔 3 人、剩 12 人」只贵 ¥0.67。后者显然才是可执行的业务建议。
容忍带（8%）是防止推荐「指标游戏解」的护栏。

### 3.5 接口（`main.py`）

请求新增：

| 字段 | 含义 |
|---|---|
| `per_capita_cap: float?` | 人均上限（元/人）。`null` = 不约束。≤0 时 400 |
| `exclude_ids: [str]` | 人工确认后要剔除的乘客**稳定 id**。剔除后不足 `PER_CAPITA_MIN_SERVED` 时 400 |
| `passengers[].id: str?` | 乘客稳定 id。缺省按提交顺序回退 `P001/P002...`；重复 → 400 |

响应（`TaskResult`）新增：

| 字段 | 含义 |
|---|---|
| `served_count` | 实际参与人数（= 坐车人数） |
| `per_capita_cost` | 人均车费 |
| `per_capita_cap` | 本次设置的上限 |
| `excluded_ids` | 本轮已剔除的稳定 id（**主键**，回显） |
| `excluded_names` | 同上，姓名口径（仅展示） |
| `exceeded` | 人均是否超上限 |
| `drop_suggestion` | 建议对象：`cap` / `current_per_capita` / `achievable` / `best` / `suggestions` / `strategy_counts` / `note`；每个建议项含 `drop_ids` + `drop_names` |

任务级（`_job_payload`）也回显 `per_capita_cap` / `excluded_ids` / `excluded_names`，轮询期间即可读。

**不新增任务状态。** 超限时不进入「等待确认」态，而是：本轮正常完成并附带建议 →
人工确认后**发起一次新的求解**（带 `exclude_ids`）。理由：A8 的 8 态枚举已定稿，
加第 9 态会破坏既有契约；而「重算」本来就是一次新的求解，语义更干净。

### 3.6 落库（`db.py`）

- `carpool_task` 就地补列 `per_capita_cap` / `excluded_ids` / `excluded_names`
  （`_EXTRA_COLUMNS` + `ALTER TABLE`，老库自动升级）；`passenger.ext_id`、
  `route_passenger.passenger_ext_id` 同理。
- **人均不单独存列**：由 `total_cost ÷ Σ route_passenger 行数` 现算
  —— 被剔除者天然不在分母里，也不会因为补列而破坏老库。
- 乘客表只写**实际参与**的人（被剔者不写），保持「库里的人 == 方案里的人」不变式；
  因此被剔名单必须单独存 `carpool_task.excluded_ids/names`，重启后仍能如实回显。
- 明细里的 `passenger_ext_id` 让「人 → 分摊金额」的映射在重启后依然按 id 对齐，不依赖姓名。

### 3.7 前端（`index.html`）

- 创建页新增「人均车费上限」**下拉选项**：`不限 / ¥2 / ¥4 / … / ¥30`（步进 **¥2**）。
  业务反馈：固定 10 元不是刚需，**能快速横向对比不同上限下的方案**才是。
  下拉把「试几个值」的成本从「改数字 + 重提」降到「选一项 + 重提」，且天然规避非法输入。
- 结果列表头追加 `· 人均 ¥x.xx（上限 ¥y.yy，已超出/未超出）`。
- 超限时在列表下方渲染建议卡片：可达性 + 根因 + 建议名单（chip 标签）+
  「确认剔除并重算」按钮 + 「被剔除者将不能参加本次活动」提示。
  chip 在**存在重名**时追加灰色 `#id` 角标，两个「张伟」不再无法区分。
- **备选方案区**：达标方案未必是业务最优。实测示例名单（15 人、cap ¥10）里
  「剔 10 人 → 人均 ¥6.97」才达标，而「剔 3 人」只贵一点——这个取舍**不该由算法替人做**
  （B3 = 人工确认）。因此把 `suggestions` 里其余候选摊开成列表，
  每行显示「剔 N 人 → 剩 M 人 · V 车 · 人均 ¥X（达标/仍超上限）」并配独立「采用」按钮，
  组织者可一键切换到任意一个候选。
- `submitTask` 重构为 `buildPayload(excludeIds)` + `runTask(payload)`，
  「确认剔除并重算」与「采用备选方案」走同一路径（都传 `drop_ids`），
  并如实显示后端 400 的 `detail`。
- 乘客行改用 `addRow` 分配的稳定 id 寻址（`byPid` / `data-pid`），
  地址解析、状态标签、删除行都不再依赖数组下标。

## 4. 实测（真实接口链路）

### 4.1 示例名单（前端「载入示例」，出行较集中）

15 人 / 3 车 / ¥202.97，人均 **¥13.53**，cap ¥10 → 超限：

```
建议 → 剔 10 人（乘客04…15）→ 剩 5 人 1 车，人均 ¥6.97  ✔ 达标
备选 → 剔 3 人 / 剔 4 人 / 剔 5 人 / 剔 6 人（各自人均一并摊开，由人取舍）
```

这条最能说明**为什么必须有备选区**：算法在「硬上限」下选了剔 10 人达标，
但业务上「剔 3 人、人均 ¥13.x、稍超一点」往往更可接受。
B3 规定由人确认，所以把两者都摆出来，而不是替人做决定。

### 4.2 构造的分散实例（15 人 / 预算 8s）

```
提交 → 全员 15 人 3 车 ¥226.15，人均 ¥15.08 > ¥10  → exceeded=True
建议 → 剔 3 人（甲、壬、癸），剔除后 12 人 2 车 ¥168.75，人均 ¥14.06
       achievable=False（该实例地理分散，剔到只剩 9 人时人均反而回升到 ¥14.03）
```

人工确认后带 `exclude_ids` 重算（前端传的是 `drop_ids`，不是姓名）：

```
结果 → ¥168.75 / 12 人   人均 ¥14.06
excluded_ids  回显 = ['p3','p9','p10']（稳定 id）
excluded_names 回显 = ['甲','壬','癸']（展示口径）
实际参与名单 = 12 人，三个被剔者均不在内  ✔
```

### 4.3 参数校验

```
剔到只剩 1 人     → 400 {"detail":"剔除后仅剩 1 人，低于最低成团人数 2"}
per_capita_cap=-5 → 400 {"detail":"人均车费上限必须大于 0"}
乘客 id 重复      → 400 {"detail":"乘客 id 重复：x1（第 1 行与第 2 行）。id 是剔除与去重的唯一主键…"}
```

### 4.4 上限扫描：**不同上限值下到底有什么区别**

> 脚本：`backend/tests/a9_cap_sweep.py`；原始输出：`backend/tests/a9_cap_sweep_result.txt`。
> 名单 = 前端「载入示例」的 15 人，终点郑州东站，离线 Haversine 矩阵（零 API 成本）。
> 基准与候选同口径（`seed=20260101`、预算 1s），故「剔前 / 剔后」可直接对比。

基准（不剔人）：3 车 · ¥187.88 · 人均 **¥12.53**

| cap | 可达 | 建议剔 N 人 | 剩余 | 车数 | 总费用 | 人均 |
|---|---|---|---|---|---|---|
| ¥4 | ✗ | 9 | 6 | 1 | ¥32.98 | ¥5.50（仍超，最接近解） |
| ¥6 | ✔ | 9 | 6 | 1 | ¥32.98 | ¥5.50 |
| ¥8 | ✔ | 9 | 6 | 1 | ¥32.98 | ¥5.50 |
| ¥10 | ✔ | **1** | **14** | 3 | ¥132.61 | ¥9.47 |
| ¥12 ~ ¥22 | ✔ | 1 | 14 | 3 | ¥132.61 | ¥9.47 |

**这张表把两件事同时讲清楚了：**

1. **阶梯效应是真实存在的**：cap 从 ¥8 放宽到 ¥10，建议**突然**从「剔 9 人」变成「剔 1 人」。
   因为 ¥8 以下时 2 车 / 3 车方案的人均都压不下去，唯一出路是把车数压到 1 辆
   （1 车最多坐 6 人 → 必须剔 9 人）；而 cap ≥ ¥10 时 3 车方案就达标了，**多留 8 个人**。
   上限不是连续调节旋钮，中间隔着「一辆车」的台阶。
2. **上限越紧，代价越不线性**：¥10 → ¥8 只差 2 元，代价却是多剔 8 个人。
   这正是把上限做成**下拉（步进 ¥2）**的价值——业务可以左右拨两下，
   一眼看出「再降 2 元要多剔几个人」，而不是先拍死一个 10 元再被动接受 9 人的结果。

> 与 §2.4 的关系：§2.4 的「人均最低 ¥12.91」是**真实路网矩阵**下的结论；
> 本节是 Haversine 口径，绝对值不同（本表 ¥10 即达标）。
> 结构性结论（阶梯、不可达的存在）两者一致，不依赖具体矩阵。

## 5. 关键设计决定与理由

| # | 决定 | 理由 |
|---|---|---|
| D1 | **不在 ALNS 里做子集选择**（不改为 Prize-Collecting 变体），改用外层「求解 → 建议 → 人工确认 → 重解」 | ①B3 要求人工确认，外层闭环天然满足；②内层改动会动摇 P1 已验证的搜索质量；③人均是比值型指标，罚分尺度难调且易被搜索钻空子（剔光人） |
| D2 | 候选必须含「**整车剔除**」 | §2.1：车数是唯一成本阶梯，只按距离剔人实测会**抬高**总费用 |
| D3 | 用「快速估算排序 + 少量真实求解」而非枚举全部子集 | 全枚举是 2ⁿ；估算用初始解费用（排序足够），只对 ≤4 个候选跑真解，总耗时可控（预算 8s 时约 +5~8s） |
| D4 | 未达标时用「近似同优带宽 + 保留人数最多」，而不是人均最低 | 防止「剔到只剩 2 人」这类不可执行的指标游戏解（实测该类解人均 ¥13.39，只比合理解便宜 ¥0.67） |
| D5 | `subset_matrix` 必须裁出 provider 真实矩阵 | 否则一剔除就退化成 Haversine，建议与最终方案会互相矛盾 |
| D6 | 固定 `random.seed(20260101)` 跑验证求解，并在 `finally` 里还原全局 RNG 状态 | 建议必须**可复现**（同一个任务刷新得到同一份名单），同时不能污染主搜索的随机性 |
| D7 | 不新增任务状态，确认后重新提交 | A8 的 8 态已定稿；重算本就是一次新求解，契约更干净 |
| D8 | 剔除主键用**稳定 id**，不用姓名 | 姓名可重名（一批名单里两个「张伟」很常见），按姓名剔会连坐无辜者。前端 id 只增不减、删行不重排，保证「剔除并重算」两次提交间同一人 id 不变；未传 id 的旧客户端按顺序回退 `P001…` 保证兼容；重复 id 直接 400（主键重复同样会连带误伤） |
| D9 | 上限做成**下拉（步进 ¥2）**而非数字输入 | 业务要的是「横向比不同上限下的方案」，不是某个固定值；下拉把试值成本降到一次选择，并天然消除非法输入 |

文档性质：

> 面向后端开发、数据库工程师、前端开发的系统设计文档。

# 二、数据库设计原则

## 1. 数据库选型（V1.1）

推荐：

### 主数据库：SQLite 3

V1.1 不再使用 MySQL。理由：
- V1.0 定位为单机工具，不做多用户 SaaS；
- SQLite 3 是文件型数据库，随项目目录走，零部署；
- 30 人规模数据量极小，SQLite 完全够用；
- 字段类型映射：bigint→INTEGER、decimal→REAL、datetime→TEXT(ISO8601)、json→TEXT(JSON 字符串)。

负责：
- 拼车任务
- 人员信息
- 方案结果
- 地图矩阵缓存
- 优化任务状态
- 地图配额计数

---

### 缓存：内存 + SQLite

V1.1 不再使用 Redis。地图矩阵、优化中间状态直接放 Python 进程内 dict，关键数据持久化到 SQLite。进程重启后从 SQLite 恢复矩阵缓存。

---

### 文件存储：无

V1.1 不使用 OSS/MinIO。地图 polyline 直接存 vehicle_route 表的 TEXT 字段。导出文件 V1.0 不做。

# 六、任务创建接口


## POST

```
/carpool/tasks
```


创建拼车任务。

optimization_mode 取值：`cost`（最省钱，默认）/ `balanced`（平衡）/ `fewest_vehicles`（少车辆）。
passengers 支持两种输入：
- 坐标模式：传 lng/lat/coordinate（WGS84/GCJ02/BD09）
- 地址模式：传 address 文本，后端走 geocoding 解析

请求：

```json
{
"name":"广州机场拼车",

"destination":{
"name":"机场",
"lng":113.3,
"lat":23.4
},

"optimization_mode":"cost",

"passengers":[

{
"id":"001",
"name":"张三",
"lng":113.1,
"lat":23.2,
"coordinate":"GCJ02"
},
{
"id":"002",
"name":"李四",
"address":"广州市越秀区北京路100号"
}

]
}
```


返回：

```json
{
"task_id":10001,

"status":"CREATED"
}
```

# 十三、算法调用（V1.1 同进程）

V1.1 不再独立部署算法服务。FastAPI 进程内直接 import 算法模块，用 BackgroundTasks 异步执行。

调用方式（Python 伪代码）：

```python
from optimizer import run_optimization

@router.post("/carpool/tasks/{id}/optimize")
def optimize(id: int, background_tasks: BackgroundTasks):
    job_id = create_job(id)
    background_tasks.add_task(run_optimization, job_id)
    return {"job_id": job_id, "status": "QUEUED"}
```

并发限制：同时运行的优化任务数 ≤ max(1, CPU核数 - 2)，超过的任务 status=QUEUED。

# 十四、缓存设计（V1.1：内存 + SQLite，不用 Redis）

## 地图矩阵缓存

进程内 Python dict：
```
matrix_cache[(task_id, from_point, to_point)] = {"distance": 3000, "duration": 500}
```

持久化到 `map_matrix` 表，进程重启后从 SQLite 恢复。

---

## 优化状态缓存

进程内 Python dict：
```
optimization_cache[job_id] = {"status": "OPTIMIZING", "best_cost": 520.5}
```

同步写 `optimization_job` 表，进程崩溃后从表里恢复状态。

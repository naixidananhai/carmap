# 拼车路线优化系统 7 份设计文档评审意见 V1.0

评审范围：业务需求规格、技术方案、数据库+API、前端产品设计、算法详细设计、MVP 开发计划、测试方案，共 7 份。

评审结论：整体闭环已形成，主干规则（30 人 / 4+6 人车 / 5400 秒硬约束 / 16 元起步价+3 元每公里 / 最低费用字典序）对齐良好；但存在 **8 处直接冲突**、**14 处关键遗漏**、**13 个实现风险**，若不解决就开工，会在第 2~3 周返工。

---

## A 类：文档间直接冲突（P0，开工前必须统一）

### A1. 费用尾差分给谁 —— 业务需求 vs 技术方案
- **业务需求（第 40 行）**：尾差由"本车接人顺序排在第一位的乘客承担"。
- **技术方案（第十一节）**：尾差优先分给"同车费用最高分摊金额乘客"，相同则乘客 ID 最小者。
- **测试方案（Case 3）**：100 元 3 人 = 33.33/33.33/33.34，但没说分给谁。
- **冲突后果**：同一方案跑两次，33.34 元可能落在不同人头上，乘客侧对账会不一致。
- **建议**：统一采用业务需求版（分给接人顺序第一位），因为它和"路线顺序"天然绑定、可复现、司机/乘客都好理解。技术方案版的"金额最高者"在分摊金额相同时退化为 ID 最小，和业务规则不等价。

### A2. 是否"优先 6 人车" —— 业务需求 vs 算法详细设计
- **业务需求（第 15 行）**：车型是可行性变量、非成本变量；"不存在 6 人车型优先"；5~6 人只能 6 人车，≤4 人两种成本等价。
- **算法详细设计（第四节第 2 步、第 380 行）**："默认优先 6 人，原因：减少固定成本"。
- **冲突后果**：算法会倾向塞满 6 人车，可能导致绕路、超时 5400 秒；业务需求已论证过这一点不能预设。
- **建议**：算法详细设计改为"≤4 人时两种车型都生成候选，由费用/时间评价函数自然选择"，删掉"优先 6 人"的硬编码。

### A3. 前端是否暴露"优化模式" —— 业务需求 vs 前端设计
- **业务需求（第 58 行）**：V1.0 不开放模式选择，"未开放的模式不在界面暴露"。
- **前端设计（创建任务页）**：画了"○最省钱 ○平衡 ○少车辆"三个单选。
- **冲突后果**：用户选了"平衡/少车辆"，后端却不实现，等于埋雷。
- **建议**：V1.0 前端只留"最省钱"（或干脆不显示这一栏），其余选项置灰/隐藏，等 V1.5 再开放。

### A4. 初始解 60 秒是否包含矩阵生成
- **业务需求（第 62 行）**："初始可行解预算 60 秒"。
- **MVP 计划（第九节）**：矩阵生成 <60 秒 + 初始方案 <60 秒 + 优化 <5 分钟。
- **测试方案（指标 3）**：地址解析 <10 秒 + 矩阵 <60 秒 + 初始方案 <60 秒 + 优化 <300 秒。
- **冲突后果**：按 MVP/测试口径，用户从上传名单到看到方案要 10+60+60=130 秒，与业务需求"60 秒出初始方案"的体感不符。
- **建议**：明确阶段计时口径——"矩阵生成"不算在算法预算里，是前置 IO；初始解 60 秒从矩阵就绪开始算。前端等待页要把"正在取地图数据 / 正在优化"分两段显示。

### A5. Top-K 边界值与动态扩展
- **技术方案**：≤10 人 K=100、11–20 人 K=300、21–30 人 K=500、>30 人 K=1000；停滞 60 秒时 K×2，上限 Kmax=2000。
- **算法详细设计**：10 以内 K=100、10–20 K=300、20–30 K=500、30 以上 K=1000；**没提 Kmax=2000 和动态扩展**。
- **冲突后果**：人数恰好 10、20、30 时落在哪一档歧义；动态扩展机制算法工程师不知道。
- **建议**：统一用左闭右开区间（[1,10) / [10,20) / [20,30) / [30,+∞)），并把 Kmax=2000 写进算法详细设计。

### A6. 方案对比页 —— 前端要 vs 后端没接口
- **前端设计（第十节）**：方案 A vs 方案 B 对比卡片。
- **API 设计**：只有 `GET /carpool/tasks/{id}/solution` 返回单方案；数据库 solution 表虽有 version/is_best，但没有"返回前 N 个方案"的接口。
- **冲突后果**：前端画了页面，后端调不通。
- **建议**：V1.0 直接砍掉方案对比页；V1.5 再加 `GET /solutions?limit=N` 接口。前端把这一栏标为"暂不开放"。

### A7. polyline 存哪里 —— 数据库 vs 技术方案
- **数据库设计**：`vehicle_route.polyline` 字段直接存 MySQL text。
- **技术方案（数据库选型）**：polyline 放对象存储 OSS/MinIO。
- **冲突后果**：30 人任务 8 辆车的 polyline 不大，但永久保留历史方案后 MySQL 行膨胀。
- **建议**：V1.0 直接存 MySQL text 够用（MVP 规模）；数据库设计删掉 OSS 那段，避免过度设计。等历史方案 >1 万条再迁 OSS。

### A8. 求解状态枚举不统一
- **业务需求**：7 种状态（含"达到间隙阈值结束"、"已证明最优"、"未找到可行解"）。
- **技术方案**：INIT/FEASIBLE/OPTIMIZING/STOP_GAP/STOP_TIMEOUT/STOP_STABLE/OPTIMAL/FAILED 共 8 种。
- **数据库 optimization_job.status**：只有 RUNNING/TIMEOUT/STOP_STABLE/OPTIMAL/FAILED —— **缺 FEASIBLE、OPTIMIZING、STOP_GAP**。
- **建议**：以技术方案的 8 种为基准，数据库字段补全；并把"FAILED"拆成"PROVEN_INFEASIBLE"（直达超时等已证明不可行）和"SEARCH_FAILED"（算法没找到），对应业务需求"禁止混淆"的要求。

## B 类：关键遗漏（P1，V1.0 必须补）

### B1. 地址→坐标的地理编码（geocoding）链路完全没写
- 前端 Excel 模板是"姓名 | 手机 | 地址"，但业务需求输入是经纬度坐标。
- 业务需求只写了 `geoconv`（坐标→坐标），没写 `geocoding`（地址→坐标）。
- **要补**：
  - geocoding 用百度 API，返回的就是 BD09，不需要再 geoconv；
  - 地址解析失败（找不到）怎么办——是该乘客标记 INVALID_COORD 让用户改，还是阻断整单？
  - geocoding 也按次计费，30 人 = 30 次，要计入配额预算。

### B2. 个人乘车明细字段在 API/前端缺失
- 业务需求要求逐人输出：直达时间、实际乘车时间、增加时间、绕行比例、预警。
- 数据库 route_passenger 表只有 ride_duration、direct_duration、warning —— **缺 increase_duration、detour_ratio**（虽可算但没存，导出/重查时要重算）。
- API `/solutions/{id}/vehicles` 返回的 passengers 只是 ID 列表，**没有个人乘车明细**。
- 前端"乘客查看页"只显示"预计 55 分钟 / 32.5 元"，**不显示直达时间、增加时间、绕行比例、绕路预警**。
- **要补**：API 加 `/solutions/{id}/passengers` 接口；乘客分享页加一行"直达 25 分钟，本次拼车 55 分钟，多花 30 分钟（绕行 220%）⚠"。

### B3. WebSocket 推送字段不够
- 业务需求要求等待页显示：候选路线数、当前最低费用、迭代次数、预计剩余时间、当前阶段。
- 数据库/API 设计的 WebSocket 消息只有 `{type, value}`。
- **要补**：消息体改为 `{type: "progress"|"best_cost"|"candidate_count"|"stage", stage, progress, best_cost, iteration, candidate_count, eta_seconds}`。

### B4. 司机分享页"开始导航"按钮与业务需求冲突
- 业务需求（第 278 行）："不能假设所有地图服务都支持任意数量的途经点"。
- 前端（司机版）直接画了 `[开始导航]` 按钮。
- **要补**：V1.0 改为"复制导航路线（文本）"或"在百度地图 App 中打开"（只传终点，途经点让司机自己按摘要顺序加），不要承诺一键导航。

### B5. 登录/用户体系在 MVP 计划里消失
- 数据库设计了 user 表、普通用户/管理员角色。
- 前端首页直接"创建新拼车任务"，**没有登录入口**。
- MVP 计划 8 周排期**没有登录模块**。
- **要明确**：V1.0 是单机工具（不登录、数据本地/SQLite），还是多用户 SaaS（要登录、要数据隔离）？这个决定影响第 1 周工作量。

### B6. 任务队列/异步执行没设计
- 算法要跑 5 分钟，FastAPI 同步调用会阻塞 worker。
- 数据库设计提了"算法服务独立部署"，但没写用什么协议调用（HTTP? gRPC? 消息队列?）、任务怎么排队、并发上限多少。
- **要补**：MVP 至少用 FastAPI BackgroundTasks 或简单的 Redis+RQ；并限制并发任务数（比如同时只跑 1 个优化），避免 8 核 16G 服务器被打满。

### B7. 稳定性指标（10 次跑费用波动 ≤1%）在测试方案里漏了
- 业务需求（第 349 行）：同一输入跑 10 次，总费用相对差异 ≤1%。
- 测试方案（第十八节）：连续跑 100 次，只测成功率和内存，**没测费用波动**。
- **要补**：测试方案加"稳定性"小节，明确 10 次跑费用 max-min / mean ≤ 1%。

### B8. 验收阈值"费用下降 ≥30%"业务需求没确认
- 测试方案（第十二节）定了费用下降 ≥30%。
- MVP 计划（第十一节）也写了 ≥30%。
- 但业务需求全文**没有这个数字**。
- **要确认**：这个 30% 是业务方拍的还是测试自己拍的？30 人如果本来就分散在城市两端，下降 10% 都难；如果集中在写字楼，下降 60% 都可能。建议按数据集分档定阈值（B 类集中 ≥50%、A 类随机 ≥30%、D 类反向 ≥10%）。

### B9. 小数秒的边界处理没写
- 业务需求：5401 秒即不合格、零容差、不四舍五入。
- 但百度地图 Duration 返回的是**整数秒**还是**带小数**？实际是整数秒，OK。
- 但"不四舍五入"到底是"截断"还是">=5400 合格"？5399.9 算合格还是不合格？
- **要补**：明确规则为"地图返回整数秒 duration_second ≤ 5400 即合格"，不做浮点运算。

### B10. 同坐标多人拆分逻辑在算法里没体现
- 业务需求：同坐标 7 人，6 人车也只能装 6 人，余 1 人另一辆车接，两车都停靠该点。
- 算法详细设计：DBSCAN 用 Haversine 距离，同坐标距离=0 会聚成一类；容量拆分时**没说怎么处理"同点 N 人要拆多车"**。
- **要补**：算法在容量拆分阶段加一条规则——"同一坐标点人数 > 车型容量时，必须拆成多车，且这些车的第一停靠点都是这个坐标（里程增量 0）"。

### B11. 个人乘车时间（ride_duration）怎么算没定义
- 业务需求：t_ride(i) = 从乘客 i 上车点到终点的时间。
- 路线 A→B→C→终点，乘客 B 的乘车时间 = B→C→终点，而不是 A→B→C→终点。
- 但路线里程是 A→B→C→终点的总里程，怎么拆出 B→C→终点这段时间？
- **要补**：算法必须逐段调用矩阵（B→C、C→终点）累加，或者路线规划接口返回各段 duration，不能简单用"总时间 - 到 B 之前的时间"（因为绕路会让这段不等于真实路线）。

### B12. 百度地图 AK 管理、配额告警、失败重试策略
- 业务需求提了"申请 AK、有免费配额、超了要付费"。
- 其他文档没写：AK 配在哪里（环境变量?配置中心?）、QPS 超限怎么退避、一天配额跑满怎么降级。
- **要补**：技术方案加"地图服务运维"小节，明确：3 次重试、指数退避、每日配额计数、超额时暂停任务并通知。

### B13. Excel 导入模板字段不全
- 模板：姓名 | 手机 | 地址。
- 但业务需求要的是经纬度（或至少坐标系来源）。
- 如果用户直接贴经纬度呢？模板要支持两种列组合：
  - 模式 1：姓名 + 地址（走 geocoding）
  - 模式 2：姓名 + lng + lat + 坐标系（走 geoconv）
- **要补**：前端导入页要让用户选"我有地址"还是"我有坐标"。

### B14. 费用分摊字段没存数据库
- 业务需求：尾差固定由接人顺序第一位承担，全精度计算后汇总再四舍五入。
- 数据库 route_passenger 表**没有分摊金额字段**。
- API 也没返回每人分摊金额。
- **要补**：route_passenger 增加 allocated_cost 字段（decimal(10,2)），API `/solutions/{id}/passengers` 返回每人分摊。

## C 类：实现风险（P2，开发前要明确技术口径）

### C1. 优化算法 vs 地图复核的迭代回路
- 算法在矩阵上跑出方案 → 地图复核发现某车超时 → 回到优化。
- 但 ALNS 跑了 5 分钟，复核超时后是**从当前最优重新优化**还是**从头再来**？预算怎么扣？
- **建议**：复核失败的车，把它的乘客全部 destroy，重新 repair，不重置全局 best，预算不清零。

### C2. 地图矩阵 31×31 = 961 次调用
- 30 人 + 1 终点 = 31 个点，两两对称矩阵 = 31×30/2 = 465 次驾车路线查询。
- 百度驾车矩阵 API 支持批量（一次最多多少对点？），要确认；否则 465 次单请求在 QPS 限制下要等几分钟。
- **建议**：用百度 `directionmatrix` 批量接口，一次请求多个点对。

### C3. candidate_route.passenger_ids 用 JSON 字段
- MySQL 8 JSON 字段查询/索引都不方便，30 人 Top-K=500 还行；100 人时 K=1000，JSON 查重/筛选会慢。
- **建议**：V1.0 接受，V2.0 迁到关联表 candidate_route_item(route_id, passenger_id, sequence)。

### C4. ALNS 接受准则（模拟退火）的温度参数
- 算法详细设计写了 P = e^(-Δ/T)，但**没给初始温度 T0、冷却系数 α**。
- 30 人规模 Δ 典型值是多少（几元?几十元?）？T0 设错了算法会"乱跑"或"不动"。
- **建议**：先跑 100 次迭代收集 Δ 分布，取 T0 使得初始接受较差解概率 ≈ 0.5，α≈0.995。

### C5. DBSCAN eps=1000 米对郊区不合适
- 算法详细设计默认 eps=1000 米。
- 但如果是郑州/登封这种郊区城市，乘客本来就分散，1000 米 eps 可能聚不出类。
- **建议**：eps 作为任务级可配参数，前端不暴露，但 API 允许覆盖；默认 1000 米。

### C6. 司机分享页"预计驾驶时间"和实际百度导航不一致
- 我们用的是标准行驶时间（不考虑路况），司机打开百度 App 实际导航会按实时路况算。
- 可能出现：规划 75 分钟，实际下班高峰 95 分钟。
- **建议**：司机页加免责声明"规划时间为平峰估算，实际以导航为准"，和乘客侧免责对齐。

### C7. 费用"规划估算价"的法律风险
- 业务需求反复强调"非实际支付、以滴滴为准"。
- 前端只在费用展示页小字写了一句。
- **建议**：方案总览页底部固定一条提示栏，所有页面都带；司机页/乘客分享页也要带。

### C8. 30 人全部单独叫车的 baseline 怎么算
- 测试方案要算"费用下降率 = (单独费用 - 优化费用) / 单独费用"。
- "单独费用"怎么算？每个人单独叫车，用自己起点到终点的距离，套同一个费用函数 C(D)。
- **建议**：这个 baseline 在算法跑之前就用矩阵数据算出来，存为任务的 baseline_cost 字段。

### C9. 同一坐标多乘客在地图矩阵里的处理
- 矩阵是点对的，但同坐标点对距离=0、时间=0。
- 如果 DBSCAN 把同坐标 5 人聚成一类，容量拆分时要拆成 1 车。
- 但如果同坐标 7 人，要拆成 6+1 两车，这两车的路线都从同一坐标开始——矩阵里这个点到后续点的代价是共享的，要注意不要重复计算里程。

### C10. 多人拼车时"接人顺序第一位"的确定
- 业务需求：尾差由接人顺序第一位承担。
- 但接人顺序是算法优化的结果（2-opt 后可能变化）。
- **风险**：如果 ALNS 迭代中接人顺序变了，尾差承担者就变了——这是正常的（因为方案变了），但要在最终方案输出时再确定一次，不能在中间步骤定。

### C11. 地图 polyline 编解码
- 百度 polyline 是加密的坐标串，前端展示要先解码再画到地图上。
- 前端用百度地图 JS API 直接 `decodePath` 即可，但要确认前端 SDK 引入。

### C12. 1 人开发 vs 3 人团队的架构分歧
- MVP 计划给了两个版本：3 人团队（FastAPI + 独立算法服务 + MySQL + Redis）和 1 人版（FastAPI + SQLite + Python 算法同进程）。
- **建议**：明确 MVP 走哪条。1 人版 SQLite 够用，但要预留迁 MySQL 的 SQLAlchemy 抽象层。

### C13. 并发优化任务的资源隔离
- 8 核 16G 服务器，一个 ALNS 跑满 1 个核 5 分钟。
- 如果同时来 3 个任务，3 个核被占满，其他请求变慢。
- **建议**：用进程池限制并发优化数 = CPU 核数 - 2（留 2 核给 API/前端）。

## D 类：建议（可选优化）

### D1. 业务需求文档自身的 LaTeX 残留
- 业务需求第 66 行起用了 `\\( ... \\)`、`\\[ ... \\]`、`\\{` 等转义，在纯 txt 里不渲染，阅读困难。
- **建议**：后续版本导出时把公式转成纯文本描述（"费用 = 16 + 3×max(里程公里-3, 0)"）。

### D2. 数据库表命名风格
- 有 `user`、`carpool_task`、`passenger`、`map_matrix`、`candidate_route`、`optimization_job`、`solution`、`vehicle_route`、`route_passenger`。
- `user` 是 MySQL 保留字，建表要反引号 `` `user` ``。
- **建议**：改成 `sys_user` 或 `app_user`，避免保留字坑。

### D3. 前端移动端 H5 vs 微信小程序
- MVP 计划说"暂不做微信小程序，H5 成本最低"。
- 但司机/乘客分享页最自然的载体是微信。
- **建议**：V1.0 H5 + 微信分享卡片（JSSDK）够用，不要急着做小程序。

### D4. 历史方案对比
- 用户可能想知道"上次 30 人机场拼车花了多少钱、这次是省了还是贵了"。
- 前端首页有"最近任务"列表，但没点进去看历史方案对比。
- **建议**：V1.0 不做，V1.5 加。
